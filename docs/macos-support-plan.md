## 范围与已做的决定

| 事项 | 决定 |
| --- | --- |
| 首版支持的运行环境 | Apple Silicon、macOS 14 及以上、游戏使用「全屏窗口模式」、外接 16:9 显示器、游戏保持在前台。 |
| 首版不支持 | MacBook 自带屏幕（非 16:9、有刘海，未测）、窗口模式（需另行验收）、后台运行、悬浮层、超长窗口衣柜扫描、自动启动与关闭游戏、运行中追加任务（客户端拒绝并提示，本轮结束后重新开始）。 |

## 已验证的事实

以下内容均在一台 Apple M5 Pro、macOS 27.2、外接 LG 4K 显示器（界面尺寸 1920×1080）上实测或从源码确认。

### 游戏客户端

- `/Applications/无限暖暖.app` 是 Mac App Store 分发的原生 arm64 Unreal 程序，bundle id 为 `com.papegames.infinitynikki`，最低系统版本 14.0，没有启动器。实测版本为国服 CNMac 2.11.1。
- 画面设置只有「窗口模式」和「全屏窗口模式」，窗口左上角的绿色全屏按钮不可点击。
- 游戏进程拥有 13 个窗口，只有一个带标题 `Infinity Nikki  `（末尾有空格）。必须同时按 bundle id 和去除空白后的标题定位窗口；Windows 现有的窗口标题正则可以匹配它。
- 游戏窗口始终带一条 32 点高的标题栏，标题栏以下正好是 16:9 的游戏画面：窗口模式 1600×900 设置对应 800×450 点，全屏窗口模式对应 1920×1080 点。全屏窗口模式下标题栏被放在屏幕顶端之外，窗口实际为 1920×1112，但系统接口报告为 1920×1080。

### MaaFramework 5.16.1（当前锁定版本）

- 已自带 macOS 控制器：ScreenCaptureKit 截图，输入有 `GlobalEvent`（全局事件，会主动激活目标窗口）和 `PostToPid`（定向发给进程）两种，二选一，同时作用于键盘和鼠标。
- 截图按 `SCWindow.frame` 的点数尺寸请求整个窗口，不裁剪标题栏，也不使用真实像素。后果：窗口模式得到 800×482（含标题栏），缩放后是 1195×720；全屏窗口模式把 1920×1112 的窗口压进 1920×1080，画面缩到 97.1% 并出现假的黑边。
- 每次截图都重新枚举全部可共享内容，实测延迟中位数 265 ms（窗口模式）到 460 ms（全屏窗口模式）。
- 相对鼠标移动在 macOS 控制器上固定返回失败。
- 控制器信息为 `type: "macos"` 加 `window_id`；按键整数被直接当作 macOS 键码使用，不做 Windows 键码转换。
- Mac 控制模块 `libMaaMacOSControlUnit.dylib` 是独立动态库，由主库按文件名加载，版本不一致只告警不拒绝。它的三个入口是 C 接口，但返回的对象走 C++ 虚函数并与主库交换 `cv::Mat`、`std::string` 和 JSON，所以替换版必须用完全相同的版本、头文件和依赖编译。

### 输入实测

| 输入方式 | 游戏在前台 | 游戏在后台 |
| --- | --- | --- |
| 按键，定向发给进程 | 有效 | 有效，不抢焦点，松开后无卡键 |
| 鼠标点击，定向发给进程 | 无效 | 无效 |
| 鼠标点击，全局事件 | 有效，坐标正确 | 未测（会把游戏拉到前台） |
| 镜头：定向发给进程的 `kCGEventMouseMoved`，带相对位移字段 | 有效，真实光标不动 | 无效 |

### 截图实测

- 方法 A：`SCContentFilter(display:including:[window])`，`sourceRect` 取窗口在该显示器内的矩形，输出尺寸乘以 `pointPixelScale`。全屏窗口模式下得到干净的 3840×2160，Dock 和菜单栏不在画面内。
- 方法 B：只截窗口，但输出高度多请求 32 点，再裁掉顶部 32 点。游戏画面正好 3840×2160。游戏在后台时窗口截图仍然有效。
- 窗口查找只做一次时，原生 4K 下重复截图约 50 ms，首次约 350 ms。

### 本仓库

- Tauri 客户端在 aarch64-apple-darwin 上 `cargo check --locked` 通过（5 个警告）。MXU 基座已经按后端系统过滤控制器，并已实现 macOS 窗口枚举、权限检查和控制器创建。
- Python agent 在 macOS 上无法导入：`agent/overlay_style.py` 和 `agent/map_mask/window.py` 在模块级使用 `ctypes.WINFUNCTYPE`，`agent/navigation/controller.py` 明确拒绝非 Windows 主机，约 18 个模块直接调用 Win32。
- `resource/pipeline` 和 `tasks` 下的节点动作只有 `DoNothing` 和 `Custom`，JSON 本身不含按键码。但 `agent/daily/runtime.py` 会在运行时动态构造 `ClickKey`、`KeyDown`、`KeyUp`、`Click` 等原生动作，按键翻译必须覆盖这条路径和直接调用 `controller.post_key_*` 的位置。
- 12 个离线 Python 测试脚本中只有 `scripts/test_close_game.py` 能在 macOS 上通过。CI 不运行任何行为测试，Windows 目前唯一的门槛是打包构建（其中间接执行了 `tsc` 和 Vite）。
- 客户端在 macOS 上把数据目录定为 `~/Library/Application Support/MXU`，而 agent 从安装目录推导 `config/`、`logs/`、`debug/`、`data_overlay/`。不处理的话，两边会对同一份配置使用不同的根目录。

## 架构决定

### 自编译的 Mac 控制模块

基于 MaaFramework 5.16.1 源码打补丁，自行编译 `libMaaMacOSControlUnit.dylib` 随 Mac 包发布，同时把可复用的补丁提交给上游。保持现有的创建函数签名不变，避免改动主库和绑定。补丁内容：

- 截图：预览版使用方法 A，按真实像素输出，缓存窗口与过滤器。方法 B 留作后台截图的候选。持续流式截图推后。
- 输入：按键定向发给进程；绝对坐标点击走全局事件，但不自动激活窗口；实现相对鼠标移动，定向发给进程。
- 坐标：截图和点击共用同一套换算，每个偏移只加一次。`sourceRect` 使用显示器局部坐标，点击使用全局屏幕坐标。
- 每次下发输入前检查目标窗口、焦点和几何是否仍然有效。

输入分发放在控制模块里而不是 agent 里，这样 Python 动态构造的原生动作也自动走对路径。

### Python：`agent/host/` 包

不使用 `platform` 作为包名，因为 `agent/main.py` 把 agent 目录插到 `sys.path` 最前面，会遮住标准库。包内提供四个接口，由已连接控制器的信息一次性选定后端：

- 目标窗口的身份与焦点；
- 带保证释放的输入；
- 画面几何；
- 能力清单。

启动与关闭游戏、悬浮层、凭据存储作为可选适配器。计时、识别、规划和任务会话归属保持共用，不随平台分叉。Win32 实现从现有模块原样迁入，不改行为。

### 按键

内部继续使用 Windows 虚拟键码作为按键标识，`Binding`、已保存的配置和代码里的字面量比较都不动。翻译到 macOS 键码只发生在 Mac 后端一处，「未映射」必须与键码 0 区分开（A 键的 macOS 键码就是 0）。

### Rust 与前端

- Rust 使用普通的 `cfg` 模块和函数，不引入新的控制器抽象。工作集中在路径、子进程生命周期和打包。
- 前端有五个服务写死了 Win32 窗口查找（探索、钓鱼、按键读取、路线编辑、衣柜），统一改为走一个目标选择器。

### 路径

把只读资源根目录和可写数据根目录分开，由客户端通过环境变量显式传给 agent 和它的子进程。Windows 上两者都解析为程序目录，行为不变；macOS 上数据根目录在 Application Support 下，使用 MaaNikki 自己的目录名。

### 配置

- `nikki_macos` 控制器（`type: "MacOS"`，`display_short_side: 720`，使用自编译控制模块新增的 `DisplayWindow` 截图与 `Hybrid` 输入）和 Mac 的 `agent.child_exec` 不写进仓库的 `interface.json`，而是写在 `build/macos/interface-overlay.json`，只在组装 Mac 产物时叠加（源码开发时由 `scripts/macos_dev_home.py` 组装）。Windows 包原样复制 `interface.json`，因此它与 Windows 用户看到的接口都保持不变；客户端的后端系统过滤另外保证 Windows 上不会出现 Mac 控制器。启动游戏前置任务只对 `nikki_windows` 生效，路线生成子进程在非 Windows 上已使用 `python/bin/python3`。
- 任务可用性由执行器根据能力清单检查，不只是在界面上隐藏。已保存的预设、定时运行和功能入口在下发前都要校验，不支持时返回明确原因。

## 分阶段交付

| 阶段 | 内容 | 通过标准 |
| --- | --- | --- |
| 0. 实机验证 | 已完成，见附录。 | 键盘、点击、镜头、截图均有可行路径。 |
| 1. Windows 门槛 | PR 触发的 Windows x64 CI，运行现有离线测试；对生效的接口定义、任务与选项的标识和默认值、可执行文件路径、包内文件清单做快照比对。 | 在任何代码迁移之前变绿。 |
| 2. 行为不变的重构 | 路径拆分；Win32 调用迁入 `agent/host/`，模块导入不再触碰 Win32；前端五个服务改走统一选择器。此阶段不加入任何 Mac 代码路径的行为。 | 快照不变；新旧版本在同一台 Windows 实机上对比启动、前台日常、后台模式、路线、超长窗口扫描和关闭。 |
| 3. Mac 前台预览版 | 自编译控制模块；Mac 后端；按键翻译；`nikki_macos` 控制器；任务白名单；带内置 Python 的 `.app`；完整 DMG。 | agent 能在 macOS 上导入并注册预览任务而不导入 Windows 后端；首批任务实机通过；满足下方的发布前检查。 |
| 4. 镜头与导航 | 接入相对镜头位移，逐项放开路线、钓鱼等。 | 逐项实机测试；测量识别时的画面新鲜度和「输入到画面变化」的延迟。 |
| 5. 后期 | 后台模式（仅键盘）、悬浮层（由 Tauri 客户端绘制，仅 Mac；Windows 的 GDI 悬浮层保持原样）、不依赖超长窗口的衣柜扫描、启动与关闭游戏、增量更新、镜像、凭据改用钥匙串。 | 各自单独验收。 |

阶段 3 的发布前检查：

- 签名后的应用能加载自编译控制模块，并完成「连接、截图、输入、销毁、重连」。
- agent 或客户端出错时立即停止下发输入，按住的键和鼠标被释放。
- 游戏窗口重建后能重新连接。
- 连接时以及窗口、模式、显示器或缩放变化后，在一个已知界面上校验画面：缩放后必须正好是 1280×720，且已知界面元素匹配。校验失败时暂停输入。
- 在真实点击位置上测试 Dock 和菜单栏滑出的情况，以及按下与抬起之间失去焦点的情况。结果不确定时暂停，不重试。
- 外接显示器位于主显示器左侧或上方时，截图坐标与点击坐标的换算仍然正确。
- 桌面端和远程 WebUI 各做一次冒烟测试。

## Mac 上的任务开放顺序

| 批次 | 任务 |
| --- | --- |
| 预览版 | 邮箱最先，然后是挖掘、月卡、每周免费礼包、每月结晶兑换、常驻能力。兑换码在文字输入和剪贴板路径验证后加入。 |
| 镜头与导航之后 | 星光结晶、家园、大世界采集、自定义路线、路线测试、小游戏、星海、完整朝夕、钓鱼。不依赖镜头的路线可以提前放开。 |
| 更后或单独验收 | 幻境挑战整体、启动与关闭游戏、探索辅助、开发者子任务。 |

预览版其余五个任务在 Mac 上的现状（2026-11-24 按代码梳理，尚未实机运行）：挖掘和月卡的主路径只用已映射的按键和点击，预计可以直接验收；每周免费礼包每次都要滚动商品列表，常驻能力里的森林之光和鹰眼由鼠标右键触发（其余三种只用键盘）——控制模块补丁版本 3 已加入滚动和场景鼠标键（见 `native/macos-control-unit/README.md`），尚待实机验证滚轮方向与单位、场景里右键是否生效；每月结晶兑换受下面的既有缺陷影响，修复前不加入 Mac 白名单。

「镜头之后」那批任务（2026-11-24 夜间按代码梳理）：没有一项必须依赖悬浮层、超长窗口或后台模式。已修的代码问题：用户选「后台运行」时 Mac 改按「暂停」处理（刷噗灵小游戏按默认设置也会走到）；朝夕「每日升级」读卡片浮窗所需的悬停（控制模块的不带按下的移动改为真正的悬停）。仍待实机的共同前提：场景内鼠标键（右键、中键、左键）、滚动、相对镜头和 Option 解除光标模式、地图拖动、Ctrl 与 Ctrl+A 在 Mac 客户端的语义、文字输入。另一处已知但未改的代码问题：客户端的钓鱼、探索辅助、路线工作室、键位读取等功能用 `selectGameController` 只挑 Win32 控制器，而 macOS 上载入接口时已经移除了 Win32 控制器，这些功能在 Mac 上会提示「请先加载项目资源」；放开钓鱼前要让它在没有 Win32 控制器时选用 MacOS 控制器（Windows 上 MacOS 控制器同样被移除，行为不变），并相应调整 `scripts/test_game_target.cjs`。

开发专用开关：实机验收时要运行尚未验证的任务，可在启动开发客户端前设置环境变量 `MAANIKKI_MACOS_EXTRA_TASKS`（逗号分隔的任务入口，例如 `MaaNikki_Dig,MaaNikki_MonthlyPass`）。只有开发构建的 Mac 客户端（`tauri dev`）读取它，并在日志里逐项记录放行；agent 只在 macOS 后端读取它。发布构建既不读取，也会从它启动的 agent 的环境里去掉这个变量（此后客户端只注入 `PI_` 前缀的变量，加不回来）；这个保证只针对正式客户端及其启动的 agent，单独手动启动的 Python agent 仍会读取它。已验证的白名单仍是 `agent/host/macos/preview_tasks.json`，只在实机通过后修改。

已知既有缺陷（Windows 同样存在，暂不修复）：`agent/daily/monthly_exchange.py:41` 在结晶详情页显示「已售罄」时调用 `self.rt.back`，而 `agent/` 下没有定义 `back`（发布源码 `9a6e139` 同样没有，`c18bbaf` 引入）。这里抛出的 `AttributeError` 不在 `GameplayAction` 捕获的异常之列，任务会直接失败。触发条件是进入结晶详情页后才识别到售罄；本地已有完成记录、或在列表页就识别到售罄时会提前跳过，不会走到这一行。同一文件第 76–85 行还有一处疑点：标题不在第一屏的结晶会不经滚动直接记为已兑换。

## 如何保证 Windows 不回归

- 阶段 1 的门槛先于一切重构落地。
- 阶段 2 的每一步都是行为不变的迁移，保留 Windows 的默认值和已持久化的值。
- 为以下场景补充显式测试：虚拟键码（包括直接使用数字的调用点）、按住输入时失去焦点、借用光标期间停止、父进程退出、窗口尺寸恢复失败与重试、失效的窗口句柄。
- Mac 相关的配置变更不进入 Windows 包：`nikki_windows` 的名称、顺序、截图回退、输入方式、权限行为、可执行文件和前置任务都保持原样。
- 用旧版 Windows 客户端对同时包含两个平台资产的发布做一次更新测试。

## 阶段 2 实机验收

阶段 2 只做行为不变的迁移。CI 证明了代码能导入、离线测试与快照不变，但窗口、输入、悬浮层和启动器只有在真实的 Windows 和游戏上才能确认。验收方法是在同一台 Windows 电脑上，用现有的 v0.9.25 正式版和本分支的测试包逐项对比，两者表现应完全一致。

### 准备

1. 取得测试包：在拉取请求上加 `test-build` 标签，等「Test build Windows x64」工作流完成（约 15–20 分钟），在该次运行页面底部的 Artifacts 下载 `MaaNikki-Windows-x64-test-<提交>`。解压后得到 `MaaNikki-v0.9.25-win-x86_64.zip`、源码包和 SHA-256 校验文件。测试包与正式包同名同版本号，但内容不同。
2. 把运行包解压到一个新的文件夹，例如 `D:\MaaNikki-test`，与现有的 v0.9.25 安装并排存放，不要覆盖现有安装。
3. 关闭诊断与统计上报。测试包与正式版同为 0.9.25，如果开着上报，测试中故意制造的错误会混入项目方的正式数据。正式构建没有用于此事的环境变量或开关，唯一的方式是设置中「帮助改进软件」下的四个开关：「错误与运行诊断」「路线与坐标调优」「祝福闪光统计」「任务偏好与挖掘统计」。客户端启动时就按配置文件决定是否开启上报，缺少的项按开启处理，所以要在测试包首次启动之前就让它们为关闭：先在现有的 v0.9.25 中关闭这四项，再完全退出 v0.9.25（设置会延迟保存，退出后才确定写入）。
4. 如果要测美鸭梨相关功能（第 8 项），先在 v0.9.25 中登录美鸭梨。然后从现有安装复制 `config/` 和完整的 `data_overlay/`（如果有）到测试文件夹，使预设、任务选项、账号状态、自定义路线、按键设置、热更新数据和上一步的上报开关一致。不要复制 `logs/`、`debug/`、`cache/`，以免与新记录混在一起。复制后用记事本打开测试文件夹中的 `config/mxu-MaaNikki.json`，确认 `settings` 中 `helpImproveSoftware`、`helpImproveRouteTelemetry`、`helpImproveBlessingStats`、`helpImproveTaskStats` 四项都明确写着 `false`。之后可以在 v0.9.25 中重新打开上报。这四个开关只关闭诊断与统计上报，不是断网：更新检查（会带上版本号）、数据更新、美鸭梨、兑换码列表和幻境预测仍会访问各自的服务。
5. 阻止测试包自动更新。客户端启动时和之后每 6 小时检查一次更新，发现更新的正式版会自动下载，并在空闲时**自动安装**，覆盖测试包，没有关闭这一行为的设置；正式版几乎每天发布。**首次启动测试包之前**，在 Windows 防火墙中为测试文件夹里的 `MaaNikki.exe` 添加一条阻止出站连接的规则（只针对这个文件，不影响正式版），然后再启动测试包。这会挡住客户端自身的更新检查与下载、数据更新和诊断上报；任务由 `python\python.exe` 运行，美鸭梨收集进度和兑换码列表由任务读取，不受这条规则影响。如果设置里填了本机的「网络代理」地址（例如 `http://127.0.0.1:7890`），更新会经代理绕过这条规则：在第 4 步复制 `config/` 之前，先在 v0.9.25 中清空代理地址（复制后可恢复）。测试包启动后点「检查更新」，确认显示「检查更新失败」。如果某项功能因这条规则而异常，记为「受防火墙影响」而不是失败。已经下载好的更新包仍可在本地安装，所以测试包一旦下载过更新，就删除测试文件夹重新解压。
6. 两个版本不要同时运行：它们会争用同一个游戏窗口和鼠标保护。切换版本前完全退出另一个客户端（包括托盘）。

## 风险

按影响计划的可能性从高到低排列：

1. 自编译控制模块与官方主库在打包后的应用里能否稳定配合。目前只核对了加载方式，没有编译过。
2. Dock 或菜单栏滑出遮住游戏边缘，全局点击落到它们上面。方法 A 的截图里看不到它们，所以画面正确不能证明点击到了游戏。
3. 全局点击与焦点切换之间的竞争。
4. 重构期间的 Windows 回归。
5. 截图延迟对时间敏感任务（钓鱼、转向、连招）的影响。
6. 临时签名下的权限归属与重新授权，以及两端共用的数据路径。
7. 国际服客户端、其他显示器配置与国服实测结果的差异。
8. 客户端控制器生命周期里两处与平台无关的问题，Windows 现状同样存在，阶段 3 只为 Mac 连接处理、不改变 Windows 行为：一次运行结束时先通知前端「运行结束」再停止 agent，若此时已紧接着开始新的运行，停止的可能是新运行的 agent（Mac 连接已改为在通知之前取走这次运行的 agent 和代数）；删除实例和切换资源时在持有实例锁的情况下析构原生句柄，析构没有期限（Mac 预览版暂不处理，Stop 与重新连接的期限保证不覆盖这两项操作）。Mac 预览版限定单客户端，以下两项也留到之后：两个客户端同时启动同一实例时，被拒绝的一方界面会显示失败，它的回滚请求虽不会动另一轮的 agent 和连接，但前端没有区分「忙碌」；删除后重建同 ID 实例时，旧实例上被取消的启动只按令牌撤销，开放实例重建或并发启动前应再复查这条路径。另一个具体交错：一次真正执行的停止 agent 请求返回后才按实例当时的代数安排释放连接，若另一客户端在它断开期间已开始新的运行，释放会读到新的代数；开放多客户端前，应在取走句柄时一并记下代数并按它释放。
9. agent 进程里有两份 OpenCV：pip 的 `cv2` 和 MaaFramework 的 `libopencv_world` 都带 AVFoundation 摄像头回调类 `CaptureDelegate`，macOS 启动 agent 时提示「implemented in both」，运行时只保留其中一份。只有打开摄像头（`VideoCapture`）时才会实例化这个类，agent 和 MaaFramework 都不读视频、也不开 HighGUI 窗口，当前邮箱路径上未观察到影响；PyPI 没有不带 videoio 的 OpenCV，暂不消除这条提示。离线测试 `OpenCvUseTests`（`scripts/test_host_imports.py`）拦截 agent 对 cv2 视频与窗口接口的直接调用（含 `import cv2 as` 别名和 `from cv2 import`）；它防常见误用，但不能证明所有路径都无害（例如先把模块赋给别的变量再调用就查不到）。
10. 场景鼠标键与界面 Stop：用户从界面按 Stop 时，主库 5.16.1 的 `post_stop()` 只立即释放登记了 `auto_up` 的输入，而 agent 经 Python 绑定原始的 `post_touch_down` 发出的场景键不在其列，控制模块也收不到信号。因此 Stop 恰好落在场景键的检查期间时，这一次右键仍可能在 Stop 之后按下，正常收尾时 agent 的 `finally` 请求松开，任务结束时 `inactive()` 会重试仍按住的触点；只有释放持续失败时才可能残留按住；滚动最坏多发一次在途的滚轮。单用户正常操作可以碰到，但后果是多一次能力触发；在常驻能力（森林之光、鹰眼）放开前用有人值守的实机测试确认，或改用带 `auto_up` 的 pipeline 动作接入主库已有的释放机制。
11. 控制模块在 CI 上只能在 Intel runner 上构建：GitHub 没有给这个仓库分配 Apple silicon runner（macos-15、macos-26 都没拿到）。CI 证明的是「arm64 单元能交叉编译、加载命令和架构正确」和「同一份源码的输入逻辑测试在 x86_64 上通过」；发布出去的 arm64 二进制的行为仍然只在这台 Mac 上验证过（本机构建时运行测试，加上对官方主库的生命周期探针）。如果将来发布 CI 交叉编译出的单元，要先在 Apple silicon 上用同一 SHA-256 的文件跑生命周期探针。
12. 网页端（远程浏览器访问客户端，`http://127.0.0.1:12701`）：2026-11-24 编排方用无头浏览器在 macOS 开发环境里修改转向设置，未能可靠保存：页面加载和每次改动都会连续发出多个 `PUT /api/config`，其中一部分返回 500「写入配置文件失败: No such file or directory」；配置写入共用一个固定的 `.tmp` 文件，并发保存相互竞争是可信的解释，尚未核实；WebSocket 握手得到 200 而不是升级，网页收不到实时事件；转向下拉框的选择没有生效。同一设置在客户端界面里改动则正常保存。尚未查明是既有问题还是 macOS 数据目录改动引起；计划里把远程网页端冒烟测试列为发布前检查，发布前要先查清。
13. 实机运行依赖维护者的远程会话：2026-11-24 远程会话（UU远程）断开后 Mac 锁屏，游戏失去前台，正在运行的任务按设计暂停（只轮询停止，不截图、不发输入），解锁后游戏回到前台就自动继续。这是预期行为，但解锁时任务会立刻恢复；需要先停止的话，只有在解锁后游戏仍处于后台时，才能先在客户端停止、再切回游戏；如果解锁时游戏已经在前台，任务可能在操作者点停止之前就恢复。有人值守的实机测试期间，监视日志的匹配词要覆盖暂停与恢复消息（「游戏已离开前台」「游戏已回到前台」）。
