### 怎么上手

1. Python 环境：仓库根目录的 `.venv`（Python 3.12，装 `requirements.txt`）；MaaFramework 是 pip 包里的 5.16.1，`maafw/` 链到它。
2. 运行器：`.venv/bin/python scripts/android/runner.py run <任务入口> [--option 名=选项] --purpose "为什么跑"`，`tasks` 子命令列出安卓接口里的任务。它用叠加文件里的控制器（Maatouch + RawWithGzip）连接，加载两层资源，带 `PI_CONTROLLER` 启动 agent（数据目录 `.build/android/runner-data`，不碰客户端的数据），跑完把结果写进 `.build/android/runner-runs.jsonl`，框架日志在 `.build/android/runner-logs/<时间>/`，agent 给用户的消息在 `runner-data/debug/messages/`。
3. 探针：`scripts/android/probe.py`（`--screencap gzip`，现在模拟器连不回电脑，netcat 用不了）：`capture`、`screen --frame/--live`（只读，按动作表分类）、`reco`、`bgcheck`（会点开奇想日历再关上）、`tap`/`swipe`/`key`（都要写 `--purpose`，记进 `.build/android/input-log.jsonl`）。
4. 开发客户端（客户端接线那一步才用）：`python3 -I scripts/android_dev_home.py`，再 `MAANIKKI_DEV_HOME=.build/android-dev-home pnpm --dir client tauri dev`。
5. 测试：`.venv/bin/python scripts/run_offline_tests.py --python .venv/bin/python`（基线 `scripts/fixtures/offline-test-baseline.json`；Mac 上已知的三项：原生暂停测试失败、两项只在 Windows 跑的跳过）；`cargo test --lib`（`client/src-tauri`）；`scripts/test_windows_contract.py`；`interface.json` 必须与 `main` 字节一致。

### 设备上的注意事项

- 这台机器有三套 adb 抢 5037 端口：一律用 `/opt/homebrew/bin/adb -s 127.0.0.1:5555`，外面套 `timeout`。ADB server 会卡死（`adb devices` 仍显示 `device`，但 shell 全部超时）：`adb kill-server; adb start-server`。运行器和 agent 遇到这种情况会停下并提示。
- 不要用 `osascript`/System Events，不要把窗口拉到前面、动光标、在电脑上打字；不要启动、退出、重启或改设置 BlueStacks 和游戏；模拟器或游戏没了、要登录、出现异常提示，就停止一切输入并报告。
- 账号是真号：不花付费货币、不抽卡（共鸣）、不聊天、不改账号设置、不删物品、不推主线剧情；会消耗体力、兑换次数或材料的任务，做到确认那一步之前，交给协调者决定。
- 截图里有 UID：帧只存在 `.build/android/`（不入库）；入库的测试用图只能是不含 UID 的小块裁剪（`scripts/fixtures/android/`）。
- 每次设备会话开始和结束各做一次 `bgcheck`。会话结束时让游戏回到大世界。
- 模拟器里现在有一个 `tun0` 网卡（推断是 VPN 或加速器），它连不回电脑，所以 RawByNetcat 用不了（决定 5）。

- 页面上的点击走 `host/android/pages.py` 的 `tap_on_page`：只在预期标题的页面上、目标被认出时点；危险词在**整张截图**上读完整的标签，任何一个标签的框离要点的地方不到 40 像素就不点，而且整个任务停止、不再往回走（裁一小块来读会把「删除」截掉）；可以要求两张截图上都满足额外的条件（邮件里是「领取全部」亮起）；在新截图上确认后以它为依据发送。邮件领取之后只认「同一张截图上是邮件页、有「领取全部」、而且变灰」才算成功，其他画面都停下不点；任务结束后的返回只从邮件页和美鸭梨菜单页往回走。

### 按住触点的设备读数（2026-11-26）

实测（BlueStacks Air，Android 13，记录在 `.build/android/held/`）：用探针在大世界空地 (900,330) 按住一个不动的触点：

- 按住时，`dumpsys input` 的 InputDispatcher 部分是 `TouchStatesByDisplay:` 加一行 `0: down=true, split=true, deviceId=-1, ...`，下面列出游戏窗口和 `pointerIds=0x80000000`；抬起之后变成 `TouchStates: <no displays touched>`。`deviceId=-1` 是注入的事件（MaaTouch 用 `injectInputEvent`，没有输入设备）。
- 按住时结束设备上的 MaaTouch 进程（`kill`，两次，结果相同）：设备一直报告 `down=true, deviceId=-1`，12 秒后仍在；**而框架对之后的抬起照样报告成功**（探针的 `up` 一步 `ok: true`），画面和设备状态都说明它没有抬起。也就是说，框架报告的「抬起成功」证明不了触点抬起了。
- 在同一个点上再点一下（新的 MaaTouch 进程，按下加抬起），设备马上回到 `<no displays touched>`；之后的画面是正常的大世界。读一次约 20 ms。

用法（`agent/host/android/target.py`：触摸状态只认上面两种见过的格式；`RecentQueue` 是 InputDispatcher 最近派发的事件，每个带 `deviceId`、`eventTime`、`action`，条目数必须和标出的 `length` 一样，少了就当作读不出）：

- **发送之前**：agent 每截一张用来做判断的图，都在截图之前读一次设备（触摸状态和最新事件时间），和这张图一起记下。依据这张图的触摸，只有在那次读数报告没有按住的触点时才发（否则不发、停止所有输入，读不出也一样），读数里的最新事件时间就是这次触摸的基准。这样判断和发送之间没有多出设备读取（第三轮审查：发送前现读一次会让判断变旧，游戏里弹出的窗口看不出来）。
- **发送之后**：框架报告成功还不够（框架写进 MaaTouch 的管道就算成功，MaaTouch 还没处理也一样），要在设备上看到**这次触摸的抬起**：`RecentQueue` 里有一个 `deviceId=-1`、`action=UP`、时间晚于基准的事件，并且没有按住的触点（最多读 6 次，间隔 0.15 秒）。只看「没有按住」不够：MaaTouch 还没处理按下时，派发器也是空闲的（Codex 第一轮审查指出）。没看到就按没有确认处理（停止所有输入，标记留下），记录里写 `unconfirmed: device reports injected`、`... no new lift` 之类。
- **留下的标记，只由运行器按设备读数清除**：触摸标记里记着这次触摸针对的设备，ADB 序列号加上设备的启动号（`/proc/sys/kernel/random/boot_id`，和截图前的触摸读数在同一次 shell 调用里读、随图记下，判断和发送之间不再读设备；同一个转发地址换成了另一台模拟器、或者模拟器重启过，启动号都不同）。运行器在**连接模拟器之前**、拿到 `owner.lock` 之后，用**一次** `adb shell` 依次读启动号、进程表、`dumpsys input`、再读一次进程表（`RECOVERY_READING`；进程表要完整：`ps` 的退出码是 0、有表头、有 init、至少 20 行，两次进程表的行数相差不超过约一成），只有在：标记记的就是这台设备（序列号和启动号都一样）、没有按住的触点、派发器里没有排队的输入（`PendingEvent: <none>`、`InboundQueue: <empty>`）、读派发器之前和之后都没有 MaaTouch 进程（类名 `com.shxyke.MaaTouch`；所以上一个发送者写进去的命令不可能还在路上，也不可能在读派发器的时候才送到）时，先把清除写进输入记录（`RecoverMarker`，写不进去就不清除），再删掉标记；运行记录的 `marker_recovery` 也写明。给了指纹但对不上时直接拒绝。其余情况都和以前一样停下、要人决定。
- **agent 不自己清除标记**（客户端那条路）：预留触摸时碰到标记一律停下；客户端启动时清除标记的做法不变（重启 MaaNikki 是人做的决定）。第二轮审查找出 agent 在运行中清除标记的几种问题（上一次的按下还在 MaaTouch 里排着、清除失败后同一次运行又重试、两次读数来自不同的设备），所以收窄到运行器连接之前这一个时刻。即使标记被客户端启动时清掉，下一次触摸之前的检查仍然会拦住还按着的触点。
- 记录，不修（前提在正常使用中不出现，出问题时是安全的或与以前相同）：（1）同一台模拟器上同时有别的程序在注入触摸（另一个数据目录的运行器、`adb shell input`），它的抬起可能被当作这次触摸的抬起；只靠时间和设备号认不出是谁的，要按坐标认（设备坐标是竖屏的、要按旋转换算），没有做。这种情况下这次触摸的确认不会比改动前更弱（改动前只看框架的返回）。（2）判断用的截图和最后的焦点核对之间，游戏里弹出的窗口（焦点不变）看不出来；这个时间窗和改动前相同（设备读数随截图一起读，没有加长它）。（3）ADB 一开始就不通时，运行器在看标记之前就停了，不打印指纹（安全：标记留着，什么都不发）。（4）`dumpsys input` 的输出恰好在最后一个事件的行尾之前被截断（每行要以 `age=…ms` 结尾才算完整，截在行中间的能认出来；只截掉行尾一小段的情况没有专门防），和（1）一样只会让确认变得不比改动前更严。（5）截图之后、发送之前，别的程序开始按住一个触点：这一下照样发出，发出后读到 `other` 就停下并留下标记；前提是同时有别的输入源。（6）设备上恰好有别的进程的参数里带着 `com.shxyke.MaaTouch`（例如有人在设备上 `grep` 它），运行器会当作 MaaTouch 还在而不清除标记（安全：标记留着）。（7）截图前读设备触摸状态时 ADB 连续失败，这次截图作废、任务停下，但进程没有进入「停止所有输入」，ADB 恢复后后面的任务会重新判断（安全：没有依据旧图的触摸）。第四轮审查之后不再给标记处理加新机制，除非设备上真的出了问题（协调者，2026-11-26）。
- 设备上验证过（2026-11-26 00:30–00:53）：真的留下一个按住的触点（结束 MaaTouch）再放一个标记，运行器拒绝并报告「设备读数 injected」；清掉之后同一个标记被自动删除，「安卓检查」跑通。第三轮审查之后（01:03）：同样放标记，新的读数（进程表在派发器前后各读一次）报告正常，标记先记录再删除，邮件 4 次触摸全部确认（每张判断用的图都带着截图前的触摸读数）。第三轮的做法：放一个记着这台模拟器序列号和启动号的标记，运行器用一次读数确认（没有按住、没有排队、没有 MaaTouch）后先记录再删除，接着邮件跑通，4 次触摸都在设备上看到各自的抬起之后才记为确认，从发出到确认约 0.55 秒；探针按住触点时同一个读数报告 `state: injected, maatouch: True`，抬起、探针退出后报告 `none, False`。
- 不能做的：读到还按着时不自动去抬起。在同一个点上补一次按下和抬起确实能清掉，但那等于在没有重新判断的画面上补完一次点击，所以仍然交给人。

### 做一个新任务的办法（邮件的经验）

1. 先用已存帧和 `probe.py screen --frame`、`reco` 弄清页面：标题（页面标题 OCR 读出的文字，例如「美鸭梨」「邮件8/300 i」，用 `startswith` 比较）、要点的东西（模板要**加掩码**，只比较图标本身的像素，背景会随场景变；按钮文字用 OCR）、危险按钮在哪里。新的节点放 `resource_android/pipeline/`，模板放 `resource_android/image/android/`（不含 UID 的小块裁剪）。
2. 写一个小脚本，用 `probe.Recognizer(..., android_layer=True).on_one_frame(...)` 在所有相关的已存帧上跑真实 MaaFramework（多个识别器在同一进程里时要保留对它们的引用，否则后面的会报「probe action did not run」），确认要点的位置、危险词检查、按钮状态，再上设备。
3. 任务代码放在 `agent/host/android/<任务>.py`（Windows 包不带这个目录），共用的任务类只在入口加「触摸目标就转到安卓流程」的分支。页面上的点击只用 `pages.tap_on_page`；从大世界出发用 `rt.key("menu")` 和快捷入口，离开用 `rt.leave_page()`，结束时回到大世界。入口加进 `agent/host/android/tasks.json` 的 `experimental`，说明里写清哪一步还没在设备上见过。
4. 设备上用运行器跑，会话前后 bgcheck；看运行记录里的 `touches`（每次触摸实际点下的像素和结果）和 agent 的消息，确认之后没有留下 `touch.json`。
5. 危险词守卫（`MaaNikki_Android_Forbidden`：删除、购买、充值、共鸣、确认退出）在整张截图上读完整标签，检查它们的框是否进入要点的地方周围 40 像素；新页面上如果有别的会花钱、删东西或确认提交的字，要加进这个列表，并在已存帧上确认守卫读得到它们。

## 客户端接线的设计（阶段 C，邮件之后）

目标：维护者在客户端里选安卓控制器、按「开始」，任务在模拟器上运行。B5b-1 曾试过把 Adb 接进客户端共用的开始/停止/重连/回调流程（本地分支 `wip-b5b1-lifecycle`），审了 5 轮仍不收敛，每轮都找出新的时序问题，其中不少落在原生 Mac 也走的共用代码里。所以按协调者定的原则重做：**安卓有自己的运行归属，只在按控制器类型分开的安卓代码路径里；靠拒绝缩小状态空间，而不是处理每一种时序**。

### 不能改的共用函数

这些函数里 Windows 和原生 Mac 的行为一行不改；允许的改动只有在入口处加一个「是 Adb 就转到安卓路径」的早返回分支：

- Rust：`start_tasks_impl`（只在开头加分支）、`claim_macos_run` 和 `mac_connection.rs` 全部、`stop_agent_impl`、`stop_task_impl`、`handle_task_callback`、`finish_macos_run`/`complete_macos_run`、`connect_controller_impl` 里 Mac 的 `attach` 路径、`admit_batch_on` 对 Win32/MacOS 的规则、`schedule_release*`。
- 前端：Win32/MacOS 的连接和开始路径（`ConnectionPanel.tsx`、`Toolbar.tsx` 里非 Adb 的分支）、`macTaskTiers.ts` 对 macOS 控制器的用法。

### 安卓的运行归属

- 新的 Rust 模块（例如 `commands/android_run.rs`）持有**整个进程唯一**的安卓运行槽：`空闲 → 启动中(令牌) → 运行中(令牌) → 收尾 → 空闲`。安卓的 Tasker 每轮新建，它的回调带着本轮令牌，令牌对不上的回调一律忽略。
- 开始：只有在「空闲」且能以非阻塞方式拿到 `owner.lock`（拿到后立即放开）时才开始；用控制器定义里的掩码（Maatouch + RawWithGzip）连接，带 `PI_CONTROLLER` 启动 agent，提交时管线覆盖一律是 `{}`（风险 16），只整批开始、批次非空、配置了 agent（B5b 已有的 `android_start_refusal`）。
- 停止：令牌所属的那一轮转为「收尾」：`post_stop`、断开 agent、等子进程退出；**子进程退出并且 `owner.lock` 能拿到之后**才回到「空闲」。
- 运行中（启动中、运行中、收尾）对这个实例的重连、换控制器、销毁资源一律拒绝并说明原因（模拟器或游戏自己没了时，这一轮失败并收尾）。
- 前端：四处 Adb 连接（`ConnectionPanel` 的 `handleConnect`、`handleSelectAdbDevice`，`Toolbar` 开始任务时的两处）用控制器定义里的掩码覆盖设备发现的结果；按实例选中的控制器取档位（Adb 用 `get_android_task_tiers`）；「收尾」期间开始按钮给出提示。

### 预览版的限制（写进界面文字）

同一时间只有一个安卓实例在运行；运行中不追加任务、不改选项；运行中重连、换控制器或销毁资源被拒绝（运行整轮原子取消只在模拟器自己断开时发生）；停止之后，在 agent 子进程退出并放开 `owner.lock` 之前，下一次开始被拒绝并提示稍后再试。

### B5b-1 审出的问题和这个设计怎么对待

| 问题（B5b-1 的审查） | 处理 |
| --- | --- |
| 换成别的控制器类型后，旧 Tasker 的停止回调结束了新的一轮、取走它的 agent | 安卓回调按本轮令牌过滤；运行中拒绝换控制器 |
| 运行中重连（连接池复用同一台模拟器）或销毁资源丢掉了 Tasker，这一轮卡在「运行中」 | 运行中拒绝这些操作；模拟器断开时这一轮失败并收尾 |
| 手动停止后 agent 还在收尾，下一轮已经开始，动作重复注册 | 「收尾」一直到子进程退出，期间开始被拒绝 |
| 收尾返回时子进程还拿着 `owner.lock`，下一轮的 agent 拿不到锁 | 回到「空闲」的条件包括能拿到 `owner.lock` |
| 任务列表条目 ID 重复时，第一个结束就把整批判为结束 | 安卓开始时拒绝重复的条目 ID；Windows 上是既有行为（同样按条目 ID 判定），记录不改 |
| （更早）重连等待期间按停止被绑定清掉（风险 12） | 停止把「启动中」的令牌作废，提交前核对令牌 |
| （更早）陈旧的启动停掉了替代它的启动 | 一个进程只有一个安卓运行槽，第二次开始直接拒绝，不排队 |

### 实现和设备验收（2026-11-26）

- 实现：`client/src-tauri/src/commands/android_run.rs`（只在 macOS 上编译）。整个进程一个安卓运行槽：空闲 → 启动中 → 运行中 → 收尾 → 空闲，这一轮的 Tasker、agent 客户端和子进程都放在槽里，不放在实例上，共用的停止和清理代码碰不到它们。共用函数只在入口加了 `#[cfg(target_os = "macos")]` 的分支：`start_tasks_impl`（准入和 `android_start_refusal` 通过、目标是 Adb 之后转到 `android_run::start`）、`stop_task_impl` 和 `stop_agent_impl`（这个实例有安卓运行时由它停止）、`connect_controller_impl`（运行中拒绝；Adb 连接固定输入方式 Maatouch、截图方式 RawWithGzip，覆盖设备发现给的掩码，两条连接路径和 HTTP 接口都经过这里）、`destroy_instance_impl`、`load_resource_impl`、`maa_destroy_resource`、`run_task_impl`、`disconnect_controller_impl`、`override_pipeline_impl`（运行中，包括收尾，一律拒绝）、`post_click_impl`（Adb 实例上的直接点击一律拒绝：它绕过 agent 的守卫和输入记录）、`maa_is_running` 和状态快照（槽里正在运行的实例报告「运行中」）。准入：macOS 上 Adb 按安卓清单逐个入口准入，其他系统照旧整批拒绝；共用流程的绑定那一步发现连接中途换成了 Adb 时，在 macOS 上拒绝。
- 开始的条件：整批、每个任务都有任务列表条目且不重复、正好一个 agent；槽是空闲的；这个实例没有正在进行的连接；`owner.lock` 能马上拿到；实例上是已连接、没停止的 Adb 控制器（否则提示重新连接，开始时不自动重连）。每轮新建 Tasker，回调带本轮令牌，令牌对不上的忽略；提交的管线覆盖一律是 `{}`（风险 16）。
- 收尾：任务全部结束、内部停止或用户停止后进入收尾，在后台线程里：Tasker 还在跑就停止（最多等 10 秒）、断开 agent、等子进程退出（5 秒后强制结束）、等 `owner.lock` 能拿到（最多 10 秒，拿不到就停在收尾，之后每次检查都会再试）。收尾期间开始、重连、换控制器等都被拒绝并说明原因。
- 停止的路径（第二轮复审之后）：进入收尾的那一刻（用户停止时在「停止」返回之前、在任何任务统计 I/O 之前）写下 `stop.request`。Tasker 还在跑时，等 `touch.json` 消失（最多 5 秒）：消失了才 `post_stop`；期限到了标记还在，或者请求写不进去，**一律不调用 `post_stop`**（框架的停止先发抬起，正在进行的点击随后再按下，留下按住的触点），改为结束 agent 子进程、断开 client，等 Tasker 自己停下（10 秒；停不下来就留在收尾继续等，界面说明，仍不 `post_stop`）。依据：agent 的触摸经 `context.run_action_direct` 交给客户端进程里的 AgentClient，由本进程的控制器同步执行，已经交过来的点击在这里完整做完；安卓的入口节点只有一个自定义动作、没有后续节点，agent 没了任务就失败结束，不会有新的触摸。留下的 `touch.json` 照旧挡住之后的触摸。走了哪条路写进日志（`stop path`），运行器写进运行记录的 `stop_path`。第三轮复审之后：请求写不进去时，「停止」在返回之前、任何任务统计 I/O 之前就同步结束 agent 子进程（否则它还能再预留一次触摸）；运行器在 Tasker 停下之前不退出（超过 10 秒后继续等，每 30 秒提示一次，`stop_path` 记为 `agent terminated; tasker stopped late`），因为点击在运行器自己的进程里执行，进程退出在按下和抬起之间会留下按住的触点；运行器从第一个 SIGINT/SIGTERM 起就推迟之后的信号（任务运行中 SIGTERM 和 Ctrl-C 一样走停止的握手），第二次 Ctrl-C 或 SIGTERM 不会打断握手。
- 退出客户端（窗口销毁、托盘「退出」）：运行中的这一轮走同样的停止；收尾线程到达「触摸切不到了」（停止请求之后标记消失，或 agent 已结束且 Tasker 停下）之前，退出最多等 10 秒，然后结束 agent 子进程、继续退出（10 秒内没到这一步的情况见风险 28）。退出一开始就关闭安卓的开始准入（之后的开始被拒绝，已经取得槽的开始也不能提交），并取消还在启动中的那一轮：agent 握手还没返回的开始不会在退出之后提交任务；退出在同一个 10 秒里等它交还槽，或把它的 agent 交给收尾线程后结束它。
- 设备锁（第三轮复审之后）：客户端和运行器对同一台模拟器各自拿一把非阻塞的独占文件锁 `/tmp/maanikki-android-<序列号>.lock`（序列号里 `[A-Za-z0-9._-]` 以外的字符换成 `_`；第四轮复审之后目录固定为 `/tmp`，两边都不读 TMPDIR，也不跟数据目录走，怎样启动都锁同一个文件）。客户端在取得运行槽时（和 `owner.lock` 的检查一起）拿，槽回到空闲时放开；运行器在碰设备之前拿，退出时放开。拿不到就拒绝开始（「另一个 MaaNikki 进程正在驱动这台模拟器」）。锁文件不删除。只按序列号区分：同一台模拟器用不同的地址连接（例如 `localhost:5555` 和 `127.0.0.1:5555`）就互相看不见（不在这一步的范围内）。全部提交失败（任务 ID 都无效）时开始返回错误，不再当作成功。
- 前端：任务档位按实例选中的控制器取（Adb 用安卓清单，只在 macOS 上），其他控制器调用原来的 Mac 函数，新测试 `scripts/test_task_tiers.cjs` 核对两者结果相同；定时任务里等安卓档位的 Adb 实例不占着调度器的检查标记，下一分钟到点的原生 Mac 实例照常开始；开始响应回来后发现期间按过停止时，工具栏补发的停止（只对 Adb 实例）一定发出新的停止，不并入之前还没返回的那次；`attach_resource_path` 原来就会加在资源路径后面，没有改。

## 目标与范围

维护者最看重的是**后台运行、不占用电脑的键盘和鼠标**。Mac 原生客户端在后台收不到点击（见 Mac 计划「输入实测」），模拟器通过 ADB 发输入是目前唯一能做到这一点的路线。最终的「完成」是：在 MaaNikki 客户端里选模拟器，日常任务在模拟器里跑完，电脑照常可用。先支持 Mac 主机，Windows 主机同样要支持。

| 事项 | 决定或现状 |
| --- | --- |
| 首个目标环境 | Apple Silicon Mac 上的 BlueStacks Air（安卓 13，arm64），横屏 1920×1080。阶段 A 的全部实测都在这台机器上。 |
| Windows 主机 | 同样要支持，阶段 A 没有实测；MuMu、雷电等模拟器的快速截图和输入扩展只在 Windows 上有，留到对应阶段。 |
| 账号 | 模拟器里登录的是维护者的正式账号（与 Mac 客户端同一个 UID），按真实账号对待：不付费、不抽卡、不聊天、不推进剧情、不改账号设置。 |
| 不做 | root 方案、修改模拟器配置、在模拟器里装辅助应用。 |

## 证据的写法

- **【画面】**：通过 ADB 截到的画面里看到的现象（截图保存在 `.build/android/` 下，不入库，因为画面带 UID）。

## 已验证的事实

### 设备与环境

- 【设备】BlueStacks Air，安卓 13 / API 33，arm64-v8a，`wm size` 报告 1080×1920（竖屏自然方向），实际横屏显示，密度 320。游戏包名 `com.papegames.infinitynikki`，Activity `com.epicgames.unreal.GameActivity`，GLES 由 ANGLE 实现（`dumpsys SurfaceFlinger`：「OpenGL ES 3.2 (ANGLE 2.1.23985)」）。
- 【设备】输入设备只有三个：触摸设备「BlueStacks Virtual Touch」（`/dev/input/event2`，坐标范围 0–32767）、键盘「AT Translated Set 2 keyboard」和 gpio-keys，没有手柄设备（`getevent -pl`）。
- 【设备】ADB 地址 `127.0.0.1:5555`；ADB 服务会为同一台设备再加一个 `emulator-5554`。MaaFramework 的 `Toolkit.find_adb_devices()` 在这台 Mac 上能自动找到两条，adb 路径是 BlueStacks 自带的 `/Applications/BlueStacks.app/Contents/MacOS/hd-adb`。
- 【转述】这台 Mac 上有三套 adb（BlueStacks 的 `hd-adb`、另一个应用自带的 adb、Homebrew 的 adb）争用 5037 端口；曾出现设备显示为 `device` 但所有 `adb shell` 都卡住，重启 ADB 服务后恢复。阶段 A 期间所有 adb 调用都带超时，没有再卡住。
- 【画面】账号：等级 21，正在追踪的任务是「登上鸣鸣列车」。这只是当前追踪的任务，不代表整体进度：同一个 UID 在 2026-11-24 的 Mac 测试里跑过星海路线、打开过旅行任务、领过每周免费礼包。各页面实际看到的情况逐页记在「界面普查」的「到达的页面」里，不按任务推测。

### MaaFramework 5.16.1 的 AdbController

- 【设备】截图：RawByNetcat 每帧约 96–105 ms（720p），RawWithGzip 约 193 ms，Encode 和 EncodeToFileAndPull 约 590 ms；MinicapDirect、MinicapStream 和 EmulatorExtras 连不上。
- 【设备】触摸坐标按 1280×720 的画面坐标给出，由框架换算到设备像素（日志：请求 `(938,50)`，下发 `(1407,75)`）。框架从第一次截图得知画面尺寸；第一次截图之前点击会告警「Invalid image target size」，截图失败时触摸会被发到 `(0,0)`（审查者用内存控制器复现）。所以连接后必须先成功截图一次再发输入。
- 【画面】MaaFramework 的文字输入在安卓上出现了系统提示「Shell pasted from your clipboard」，说明它经设备剪贴板粘贴。电脑的剪贴板是否受影响没有检查。另外，现有兑换码任务会先读写**电脑**剪贴板再退回逐字输入（`agent/daily/redeem_codes.py`），安卓目标上这条路径必须改为设备侧，阶段 C 处理。
- 【设备】ADB 控制器没有滚轮和相对鼠标移动，滚动和镜头都要用滑动来做。

### 手柄路线

- 【设备】`/dev/uinput` 和 `/dev/uhid` 属于 bluetooth 组，shell 用户不在这个组里，打开都被拒绝（`uinput-access.txt`）。shell 建不了虚拟手柄。
- 【画面】在「触屏控制」模式下，用 `input gamepad keyevent`、`input joystick motionevent`（给的是坐标，不是摇杆轴）、`input dpad keyevent` 注入的事件，游戏没有可见反应。
- 【画面】设置「控制」页的「控制方式」有「触屏控制」和「控制器控制」两项。没有切换到「控制器控制」：切换后如果触屏失效，可能无法切回。
- 决定不测「控制器控制」模式（见「已做的决定」）。没有验证的：这个模式下游戏认不认这些事件；BlueStacks 自身把电脑手柄转给模拟器的功能（它需要电脑上的真实手柄或键盘焦点，与后台运行的目标冲突）。
- 结论：在已测的范围内手柄路线走不通，首版游戏动作映射到触摸。

## 架构决定

### 1. 后端按选中的控制器决定，在任务准入之前就确定

「游戏目标后端」由**这个实例选中的控制器定义**决定（`PI_CONTROLLER` 的 `type`：`Win32`、`MacOS`、`Adb`），连接后再用 `Controller.info["type"]` 核对一致，不一致就拒绝运行。它必须在**任务准入之前**确定，而不是进入任务会话以后：

- agent 侧：`registration.py` 在进入 `task_session` 之前就调用 `task_entry_supported` 判断任务能不能跑，所以目标后端要在 agent 启动、读到 `PI_CONTROLLER` 时确定。
- 客户端侧：Rust 按主机系统独立做准入（`client/src-tauri/src/commands/utils.rs`），前端把空的档位清单当成无效（`client/src/utils/macTaskTiers.ts`），定时运行读的是主机级的档位状态。这些都要改成按实例选中的控制器取档位清单。
- 阶段 B 的只读检查任务要有自己的明确入口，写进安卓清单，不借用 Mac 清单。

涉及游戏目标的入口（能力清单、按键与动作、焦点、几何、任务档位、`connect_target`）改用目标后端。只有在客户端**没有提交任务**的场合（agent 启动、离线测试、脚本）才回落到 `platform_backend()`；提交的任务如果 `PI_CONTROLLER` 缺失或格式不对，所有依赖目标的工作都先挂起，等连接的控制器类型确定后再准入，不能先按桌面准入再发现不一致（客户端写这个变量的地方是 `client/src/utils/piEnv.ts`）。保持按主机系统的：工作线程设置（`runtime_threads.py`）、剪贴板、悬浮层窗口、凭据存储；启动游戏前置任务维持现在「只对 `nikki_windows` 生效」的过滤；关闭游戏在进入电脑桌面的接口之前先检查目标后端，安卓目标直接拒绝。模拟器没有游戏窗口，悬浮层、16:9 窗口修正、超长窗口都关闭。

理由：Windows 上只会出现 Win32 控制器（Mac 控制器被客户端过滤掉），Mac 上只会出现 MacOS 控制器，所以对这两种控制器，目标后端与主机后端取值相同；用测试固定「Win32 控制器 → win32、MacOS 控制器 → macos」，并逐处审查约 27 处 `capabilities(platform_backend())`。

### 2. 游戏动作映射到触摸：拦截点、页面专用的关闭动作和 BACK 规则

在已测的范围内手柄路线走不通（见「手柄路线」），首版把游戏动作映射到触摸。拦截点要覆盖所有下发路径，不能只在一处：

- 按名字的动作：`Runtime.key` 和 `Runtime.hold` 在查 `GameKeys` 之前；`ForegroundInput.hold`、`key_down`、`key_up` 在查绑定之前。
- 整数键码和直接构造的 `ClickKey`、`KeyDown`、`KeyUp`（`Runtime.action`、`navigation/controller.py`、管线里动态生成的动作）：安卓目标上在下发到控制器之前统一拦下，没有触摸实现的一律抛出 `UnsupportedInput`，任务停止并说明原因。

动作的触摸实现：

| 类别 | 动作 | 实现 |
| --- | --- | --- |
| HUD 上的入口 | 美鸭梨菜单、地图、奇想日历、奇迹之旅、商城、换装 | 点 HUD 图标。HUD 布局玩家可以自定义，按标签识别（图标下有「商城」「奇想日历」「换装」等文字）；**识别不到就拒绝，不用默认坐标**（B4b 决定：「共鸣」夹在「商城」和「奇迹之旅」之间，猜错位置会点进抽卡页） |
| 随场景出现 | 交互、跳过、退出关卡、能力键 | 识别屏幕上的提示按钮再点；对话跳过点画面 |
| 持续 | 四个移动方向、跳跃、镜头 | 摇杆按住拖动、点跳跃键、滑动转镜头（像素每度在导航阶段重新标定） |

`key("menu")` 现在有两种用法：在大世界打开美鸭梨菜单，以及在不认识的页面上「退出去」。安卓上拆成两个动作：「打开菜单」只在 HUD 被识别时点鸭子图标；「离开当前页面」按页面选**专用的关闭动作**并核对到达的页面——多数页面是左上角的返回箭头，弹窗是右上角的 ✕（兑换码弹窗就是在 `(945,193)` 关掉的），确认框是「取消」。不认识的页面不盲目操作，停下报告。

BACK 的两条硬规则：只有当前页面被**正面识别**为 BACK 能关闭的页面时才发 BACK（BACK 在大世界会弹出「退出游戏」，在下拉框上会连同整个设置页一起关闭）；「退出游戏」确认框作为守卫页面识别，任何时候看到都点「取消」，绝不点「确认」。

B4b 的实现（`agent/host/android/actions.py`，识别节点和模板在 `resource_android/`）：

- **不发 BACK**：已调查的页面都有可以点的关闭方式（左上角返回箭头、弹窗的 ✕、确认框的「取消」），所以安卓后端根本不发 BACK 键，第一条规则自然满足；整数键码一律拒绝。
- **画面分类**（每一步都只用同一张确认过焦点的截图）：先查退出确认框（标题「退出游戏」和「取消」都认出才算；只认出其中一个、或检查没能完成，都当作不认识的画面）；再查弹窗：游戏的弹窗右上角都有同一个四角星形的关闭标记（兑换码弹窗和退出确认框都是，模板在 103 张帧上只在这 5 张弹窗帧上得分 1.000，其余最高 0.756）；看到这个标记时，只有**正面认出**是兑换码弹窗（标题「兑换奖励」，它的 ✕ 在阶段 A 实际点过）才算弹窗，认不出是哪个弹窗就当作不认识的画面，什么都不点。然后看左上角：鸭子图标且没有返回箭头、鸭子是**全亮**的、**并且**快捷栏读得出文字才算大世界；返回箭头且没有鸭子、箭头是全亮的、**并且**箭头旁读得出至少两个汉字的页面标题才算页面；其余都是不认识的画面。
  - 文字识别：大世界和页面都要求文字识别给出正面结果，所以文字识别不可用时（MaaFramework 这时报的是普通的「没认出」）不会把退出确认框（它后面鸭子图标仍然可见）当成大世界。用去掉文字识别模型的资源在真实的退出确认框帧上验证过：结果是不认识的画面，什么都不点；大世界和页面帧也都成了不认识的画面。
  - 亮度：已见过的两种弹窗（兑换码、退出确认）都会把后面的画面明显压暗，所以鸭子和返回箭头还要在**模板匹配到的那个框里**是全亮的（MaaFramework 的颜色匹配，HSV）。103 张帧上用真实 MaaFramework 测：大世界帧里鸭子的亮黄色像素 242–264 个、退出确认框帧上 0；页面帧里返回箭头的高亮像素（明度 ≥200）208–269 个、兑换码弹窗帧上 0；门槛都是 120。把真实退出确认框帧上的标题、「取消」和 ✕ 都抹掉之后验证过，结果是不认识的画面。这只覆盖**明显压暗**的弹窗：审查者合成的、背景只压到 90% 亮度的陌生面板仍能通过，这种弹窗目前没有见过。
- **「打开菜单」和「离开当前页面」分开**：`key("menu")` 在安卓上只在大世界里点鸭子打开美鸭梨菜单，其他画面一律拒绝；新的 `Runtime.leave_page()` 负责离开：兑换码弹窗点 ✕，页面点返回箭头，退出确认框点「取消」，已经在大世界就什么都不点。新的 `Runtime.escape(delay)` 在电脑上就是 `key("menu", delay)`，在安卓上是 `leave_page(delay)`；原来用 Esc「退出去」的五处调用（`ui.py` 的 HUD 恢复和 `back_to`、赛事嘉奖的关闭、钓鱼结束时离开、聚会聊天里的弹窗）都改成调用它，电脑上的行为不变（`escape` 在 Win32 和 MacOS 目标上就是调用 `key("menu", delay)`，有测试固定；`test_clicks` 的全部 67 个结果与 B1 之前的记录相同）。打开菜单的 `ui.menu()` 和启动游戏前置任务（安卓上不开放）仍用 `key("menu")`。
- `map` 在大世界里点小地图；商城、奇迹之旅、奇想日历、换装在标签行上用一排窄窗口 OCR 找到标签（几个窗口的位置要一致），再用以该点为中心、约一个标签宽的窗口复核仍读到这个标签，然后点标签上方的图标。复核挡住了向「共鸣」偏移的点（用真实帧验证：商城右缘 675 处通过，交界 692 和共鸣 727 被拒）。
- **动手之前在新截图上再确认一次**：标签搜索要跑几十次识别，耗时可能超过一秒，期间页面可能已经变了而焦点没变。所以判断完成后再截一张新图，确认还是同一种画面（页面还要标题相同：设置页和地图页的返回箭头在同一个位置）、要点的东西还在原处（按钮位置两个坐标偏差都不超过 8 像素；快捷入口用居中窗口在新图上重新读出标签，用新读出的位置核对两个坐标；按钮比较的是触摸实际点下的中心点，不是框的左上角），触摸以这张新图为依据发送。判断过程中的识别不再每次都读设备焦点，改由截图的标记核对：判断用的图和确认用的图在发送前都必须仍是当前的焦点代数和焦点纪元，否则整个判断重来（「已经在大世界、不用点」的结论也一样要先核对判断用的图）。用真实帧验证：设置页上决定的返回在地图页上确认不通过；快捷栏整体下移 16 像素后商城的确认不通过；大世界上决定的「打开菜单」在退出确认框和抹掉文字的退出确认框上确认都不通过。
- 看到退出确认框时，不管要做什么动作都只点「取消」，然后换一张新截图重新判断；发送前焦点核对失败（`ForegroundChanged`）在同样的次数限制内重新判断；不认识的画面不发任何输入，任务停止并说明原因，如果之前已经点过「取消」，报告里写明点过几次。其他按名字的动作（交互、跳过、移动等）和按住按键在安卓上仍然拒绝，留到后面的阶段。
- 点完以后是否到了预期页面，由调用方像 PC 上一样自己识别确认。
- 证据：在已保存的全部 103 张帧上用真实 MaaFramework（主资源加 `resource_android/`）跑 `scripts/android/probe.py screen`：大世界 58 张、页面 38 张、弹窗 4 张、退出确认框 1 张（`input/after-145818-350.png`，每个动作都只点「取消」，触摸点 `(494,480)`，与阶段 A 实际点中的 `(496,483)` 横向差 2 像素、纵向差 3 像素）、不认识 2 张（转镜头时鸭子图标不可见的两帧）。快捷入口的点取居中窗口重新读出的位置（与搜索时的估计相差不超过 25 像素），确认时在新图上用同一个窗口重读；58 张大世界帧上四个快捷入口全部能定位，在同一张帧上确认 232 次全部通过，快捷栏下移 16 像素的帧确认不通过；与阶段 A 实际点中的位置每个轴相差不超过 10 像素（最远的是 `now3` 的商城 (665,40) 和 `now5` 的奇想日历 (930,40)，阶段 A 点的是 (655,50) 和 (938,50)）。仓库里的测试用从设备帧裁下的、不含 UID 的小图（快捷栏、页面标题、退出确认框）拼出画面，由真实 MaaFramework 跑全部节点和文字识别。
- B6 起四角模板加了掩码（只比较图标本身的像素；没加掩码时鸭子在深色树林前只得 0.64，设备上第一次检查因此认不出大世界、什么都没点）：真实 MaaFramework 在 104 张帧上，大世界的鸭子 ≥ 0.93、页面 ≤ 0.38，页面的返回箭头 ≥ 0.975、大世界帧上 < 0.50；鸭子在退出确认框后面仍得 0.999，箭头在兑换码弹窗后面 0.988–0.991，这两种情况靠前面的守卫（标题、关闭标记）和亮度判断区分，五个弹窗帧都分类正确。设备上的退出确认框复核仍待做（B6 的两次 bgcheck 都是大世界）。
- 没有验证的：亮度判断依据的是已保存帧上的两种弹窗（兑换码、退出确认），其他弹窗的压暗程度没有实测；带关闭标记、但认不出是哪个弹窗的一律不点（认出的退出确认框照样只点「取消」），遇到时任务停止并说明原因；完全认不出、又几乎不压暗背景的弹窗（审查者合成的 90% 亮度面板）会被当成大世界或页面，这种情况目前没有防护，也没有见过。退出确认框在设备上的识别和「取消」在 B6 设备验收时再实测一次。

### 3. 手机识别资源：分层资源目录覆盖节点定义

新增与 `resource/` 平级的 `resource_android/`（含 `pipeline/`、`image/` 和自己的 `image/game/catalog.json`），只放与 PC 不同的部分：改了区域的节点、按倍数换的模板、手机独有的节点（例如 HUD 标签行、退出确认框）。安卓控制器在接口定义里用 `attach_resource_path` 把它加在主资源之后。

审查者在 5.16.1 上做的只读验证：客户端先提交主资源再提交附加资源；在新建的资源对象上两者都加载完之后再识别，同名图片用的是后加载的那张。但如果先用主资源识别过，再加载附加资源，已缓存的匹配不会更新。所以两层资源必须在第一次识别之前都加载完，阶段 B 写测试固定这一点。

### 4. agent 直接读模板和资源索引的地方统一走有序的资源根

`GameUI` 先在主资源的 `catalog.json` 里查条目、再读覆盖后的节点，路径缓存按相对名称，调用方传入的区域优先于节点。所以只覆盖管线节点不够：安卓独有的 `Asset` 条目会在查索引时就失败。做法是由 `app_paths` 提供**有序的资源根列表**（安卓目标为 `resource_android`、`resource`，其他目标只有 `resource`），索引合并、模板路径解析和缓存键都按这个列表走；调用方写死的区域要逐处检查，必要时改为读节点。涉及的读盘位置见「本仓库」一节。祝福闪光整理和衣柜扫描暂不开放，不改。

### 5. ADB 控制器：叠加文件加客户端接线，方式写死

`build/android/interface-overlay.json` 定义 `nikki_android` 控制器（`type: "Adb"`，`display_short_side: 720`，`attach_resource_path: ["./resource_android"]`），并写明输入只用 Maatouch、截图只用 RawWithGzip（原定 RawByNetcat，改动见下）。开发时由 `scripts/android_dev_home.py`（仿 `macos_dev_home.py`）组装开发目录。

但叠加文件本身管不住实际用的方式：手动连接和自动重连都直接用设备发现返回的掩码（`ConnectionPanel.tsx`、`Toolbar.tsx`），会把 minitouch 也带上。所以客户端接线（原定阶段 B，现在放在阶段 C 的第一个任务之后，见 B6 一行）：对 `nikki_android`，两条连接路径都用控制器定义里的掩码覆盖发现结果，并在连接后从框架日志核对实际选用的输入和截图方式（`Controller.info` 只反映配置的掩码，不能作为证据）。截图只写一种：写多种时框架是测速挑最快的，并不保证失败时按顺序退回。

截图方式的改动（B6 之前，2026-11-25 晚）：RawByNetcat 要模拟器经 `10.0.2.2` 连回电脑。阶段 A 时能用（约 100 ms 一帧），B6 开始时连不回了：框架报 `accept timeout`，手动用 `nc` 测试电脑端也收不到连接。模拟器里多了一个 `tun0` 网卡（`172.19.0.1/30`），**推断**是里面开了 VPN 或加速器，没有证实，阶段 A 时有没有它也没记录。玩家在模拟器里开 VPN 或加速器很常见，产品要能在这种情况下用，所以不去改模拟器。协调者先定的是掩码写 `RawByNetcat | RawWithGzip`、连接时测速自动选；实测（模拟器连不回电脑时）框架在测速里遇到 RawByNetcat 的 `accept timeout` 后卡住，连接 120 秒都没完成，所以按协调者给的退路改成只用 RawWithGzip：实测连接约 0.46 秒，12 帧截图 225–281 ms（中位约 236 ms）。两种方式拿到的是同样的原始画面，只影响速度。截图方式只在连接时确定，运行中不切换；运行器（以后客户端也一样）从框架日志报告实际用的方式。约 250 ms 一帧对点菜单的任务够用；对移动和导航够不够，是阶段 E 要实测的，不是假设。**不要不看这段就重试两种方式的掩码**：模拟器连不回电脑时，MaaFramework 5.16.1 的测速会卡在 RawByNetcat 上，连接整个卡住。如果导航阶段发现截图延迟要紧，再把 RawByNetcat 作为阶段 E 或 F 的问题重新评估（例如先在连接前自己测一下模拟器能否连回电脑，再决定掩码）。

理由：**明确固定 Maatouch，不让 MaaFramework 按测速或优先级挑选**。minitouch 在 BlueStacks Air 上点击返回成功却没有效果，框架无法据此判断它不可用；AdbShell 不能按住摇杆。

### 6. 任务分档：复用 Mac 的清单机制，Windows 包排除安卓文件

`agent/host/android/tasks.json` 与 Mac 的 `preview_tasks.json` 同格式（已验证、试用、不开放及原因、说明）。agent 侧的准入按目标后端读对应清单；客户端把 `get_macos_task_tiers` 推广为按实例选中的控制器读清单（见决定 1）。

Windows 打包现在复制整个 `agent/`，只排除 `agent/host/macos`（`scripts/release.py` 的 `NON_WINDOWS_RUNTIME`）。阶段 B 一加 `agent/host/android/` 就会改变 Windows 包的文件清单、让现有门槛失败。所以阶段 B 同时把 `agent/host/android`、`resource_android` 和安卓叠加文件加入 Windows 包的排除项，Windows 包在正式决定之前不带任何安卓文件。注意文件清单测试只比较路径：`agent/host/__init__.py` 等共用文件的内容会变，行为不变要靠测试保证。

### 7. 焦点：主机后台和设备焦点分开检查

- 「游戏在前台」= 设备上的输入焦点窗口（`dumpsys window` 的 `mCurrentFocus`）属于游戏包名。只认 `mCurrentFocus`：系统弹窗或桌面拿到焦点时，`mFocusedApp` 仍然显示游戏。
- 电脑这边是否在后台，与设备上谁有焦点是两回事。现有的后台输入路径在目标没有焦点但仍能截图时会照样返回成功（`agent/task_control.py`），前台路径在没有焦点时也会在启动时发 Alt 抬起。安卓适配器必须**在每次下发之前**检查设备焦点；焦点变化之后，基于上一帧做出的判断全部作废，重新截图识别。
- 焦点不在游戏时（桌面、系统弹窗或别的应用在前面）暂停，提示玩家切回游戏，切回后继续；不会自动切换应用，「游戏离开前台时」选的「回到游戏」在安卓上按「暂停」处理。只有确认游戏进程已经不在（`pidof` 明确报告没有）时才停止任务并报告；查询失败不算。不自动重启游戏。
- 截图只在游戏有焦点时算数（桌面或别的应用在前面时，画面不是游戏）。MaaFramework 在管线里自己截的图，不知道截图那一刻设备上谁有焦点；在回调里换一张图也不行：同一个判断里的原生 OCR 仍用原来那张，按像素认出「同一个判断」也不可靠（B2 审查中试过并放弃）。规则（B4 实现）：安卓上一个判断由拥有它的入口先确认设备焦点、截一张图，把这同一张图交给所有原生和自定义的子识别（`context.run_recognition(name, image)`），判断结束后再确认焦点，**观察到**焦点丢过就整个判断作废重来（两次读焦点之间焦点来回切换两次是采样的极限，再多一次读取也证明不了焦点一直在；所以动手之前还要在这张图上正面识别出预期的页面）。B4a 已在 `Runtime` 的截图里实现「截图前后各读一次设备焦点」，没有会话时也要读到肯定的结果。阶段 B 的只读检查任务按这个规则写；在此之前没有安卓任务依赖 MaaFramework 自己的截图。后台观察模式下 `Runtime.capture` 同样在 B4 处理。
- 按住的触点在停止、出错和断线时都要抬起；抬起失败或 ADB 断线后的抬起结果视为**未确认**，这是停止条件：任务结束并报告，不继续发输入。重连后画面上看起来没有按住（例如摇杆不亮）不能证明所有触点都已抬起，只能作为参考。
- 电脑这边的焦点、光标、鼠标保护、借用光标检查在安卓目标上跳过。连接时校验分辨率必须是 16:9 横屏，否则拒绝输入。
- 探针按这些规则实现了一个简化版（见附录），它的测试只覆盖探针自己的逻辑，不能代替 agent 适配器的测试。

### 8. 客户端的设备发现与连接

用 MXU 已有的 ADB 设备列表（MaaToolkit 自动发现，Mac 上已验证能找到 BlueStacks Air）。需要补的：同一设备的 `127.0.0.1:5555` 和 `emulator-5554` 去重；优先使用模拟器自带的 adb（例如 `hd-adb`），减少多个 adb 服务争用端口；按决定 5 覆盖输入和截图掩码；连接失败或 shell 卡住时给出「重启 ADB 服务」的提示和按钮。Windows 上的模拟器发现同样走 MaaToolkit。

## 如何保证 Windows 和原生 Mac 不变

- `interface.json` 不改；安卓控制器只在叠加文件里；`resource/` 下的 PC 资源不改，手机资源只在 `resource_android/`。
- 目标后端选择对 Win32 和 MacOS 控制器返回原来的后端，用测试固定；`capabilities` 的替换逐处审查，Windows 上的取值不变。
- 每一步都跑 `scripts/test_windows_contract.*`、离线测试基线和 Mac 的测试；探针和它的测试放在 `scripts/android/`，离线门槛不会扫描到。
- Windows 包排除 `agent/host/android`、`resource_android` 和安卓叠加文件（阶段 B 与安卓代码同时加入），文件清单门槛不变；共用文件内容的变化靠行为测试把关。
- 客户端改动（按实例取档位、ADB 掩码覆盖）只在选中安卓控制器时生效；Windows 上不会出现安卓控制器，直到维护者决定发布方式。

## 从 MaaAssistantArknights 借鉴什么

阅读的是 MaaAssistantArknights（下称 MAA）的浅克隆（提交 `1fda013`），放在仓库以外，只读不运行。MAA 的源码文件标明「AGPL v3.0 only」；本项目同为 AGPL-3.0，但**只借鉴思路，不移植代码，也不照抄它的端口表和路径表**。下面的条目都是按代码读到的做法（括号里是 MAA 的文件），后面写本项目怎么用。MaaFramework 自己已经实现了截图和触控方式的测速与选择，那部分不需要从 MAA 借。

| MAA 的做法 | 本项目怎么用 |
| --- | --- |
| 不在核心里挑 adb，由界面传入；自动检测时用模拟器进程旁边自带的 adb（`WinAdapter.cs`），另有「强制替换 ADB」按钮下载官方 platform-tools。端口 5037 的版本冲突没有代码处理，只在常见问题里要求所有工具共用一个 adb。 | 采纳「优先用模拟器自带的 adb」（MaaToolkit 在 Mac 上已经返回 BlueStacks 的 `hd-adb`）；把「多个 adb 互相关掉服务」写进连接失败的提示。 |
| 连接前先看 `adb devices`，已在列表就不再 `connect`；`connect` 60 秒超时，输出含「connected」才算成功；连上后读 `android_id`、系统版本、分辨率和方向（`AdbController.cpp`）。 | 连接检查照这个顺序做，并加上本项目已证明必要的两步：先成功截图一次，再用一个能看到结果的输入确认触控生效（minitouch 会静默失败）。 |
| 连接失败时界面逐级升级：启动模拟器 → `adb disconnect` → 用户允许时 `kill-server`/`start-server` → 结束所有同路径的 adb 进程（`TaskQueueViewModel.cs`、`StartSettingsUserControlModel.cs`）。 | 采纳分级思路，但不自动启动模拟器、不结束别的 adb 进程（这台 Mac 上还有其他工具在用 adb）；重启 ADB 服务需要用户点按钮。 |
| 任务中途 adb 命令失败时重连 5 次、每次间隔 10 秒、成功后重放原命令；最终失败则发出断开消息，界面停止任务队列（`AdbController.cpp`、`AsstProxy.cs`）。截图失败重试 20 次。分辨率变化时整个连接作废。 | 采纳「有限次数重连、失败就停止任务并报告」和「分辨率变化即作废连接」。**不采纳重放原命令**：重放触摸可能重复点击（例如重复确认），本项目重连后先重新识别页面再决定下一步。 |
| 分辨率必须至少 1280×720 且正好 16:9，否则报 UnsupportedResolution（`ControlScaleProxy.cpp`）。 | 与本项目的决定一致（连接时校验 16:9 横屏）。 |
| 每种模拟器一套命令模板，用继承只覆盖不同的命令；其中 Mac 用的 `CompatMac` 去掉了 gzip 截图（`resource/config.json`）。 | MaaFramework 的 ADB 控制器配置可以传 `config`；首版只用默认命令。BlueStacks Air 上 RawWithGzip 实测可用，暂不需要去掉。 |
| 启动游戏用 `am start`、停止用 `am force-stop`；没有专门的「游戏崩溃、回到桌面」检测，靠识别「连接断开」弹窗。 | 本项目用焦点窗口（`mCurrentFocus`）判断游戏是否还在前台，比靠弹窗更直接；启动和重启游戏首版不做。 |
| Windows 上的模拟器发现：按进程名识别模拟器，从注册表和配置文件读安装路径与端口（BlueStacks Hyper-V 的端口每次启动都会变，要从 `bluestacks.conf` 读），MuMu、雷电用端口推算实例序号。 | 阶段 F 参考。先看 MaaToolkit 的发现是否够用，不够再补。 |
| ADB 方式下没有窗口处理；MuMu 的「应用保活」开启且 MuMu 触控不可用时停止任务。文档说 PlayCover 窗口最小化或换到别的桌面空间时截图会失效。 | 说明遮挡和最小化的行为要逐个模拟器实测，不能假设（风险 1）。 |
| 连接设置界面：每种模拟器一个预设、带历史的地址输入框（会把全角冒号改成半角）、adb 路径选择、「自动检测」、「测试连接」按钮（连接后显示截图和截图耗时）。 | 客户端阶段参考「测试连接」：连接后显示一帧和截图耗时，再做一次可见的输入确认。 |

## 风险

1. **最小化时的行为未知**：窗口被完全盖住、应用未激活时，截图和输入都正常（2026-11-25 两轮后台采样，见「后台」一节）。最小化还没有观察到；如果 BlueStacks 最小化时降帧或暂停渲染，「后台运行」就要求窗口不能最小化。按决定，每次设备会话开始和结束时跑几分钟 `bgcheck`，拿到一次最小化的采样之前这条风险保持开放。
2. **模拟器检测**：阶段 A 没有看到游戏拒绝注入的触摸或提示模拟器，但这只说明目前没有，不说明以后没有。
3. **HUD 自定义**：玩家可以调整手机 HUD 布局，固定坐标会失效；按标签识别是主路径，坐标只是后备。
4. **界面倍数随设备变化**：1.13–1.25 倍是 1920×1080、密度 320 下的实测；其他分辨率或密度下可能不同。首版只支持 16:9 横屏，并在连接时校验画面尺寸。
5. **BACK 的副作用**：在大世界会弹出退出确认，在下拉框上会关闭整个页面。规则：只在页面被正面识别为 BACK 能关闭时才发；「退出游戏」确认框作为守卫识别并点取消。
6. **多套 adb 争用端口**：会导致 shell 卡住。所有 adb 调用都要有超时，客户端提供重启 ADB 服务的入口。
7. **minitouch 静默失败**：调用返回成功但点击不生效；客户端两条连接路径都要用控制器定义的掩码覆盖发现结果，连接后核对实际生效的方式，并做一次能看到结果的输入。
8. **剪贴板**：MaaFramework 的文字输入经设备剪贴板粘贴；现有兑换码任务先读写电脑剪贴板，安卓目标上必须改为设备侧，否则会动到用户电脑的剪贴板。
14. **吞掉 `UnsupportedInput` 的辅助流程**：安卓上不支持的输入会抛出 `UnsupportedInput`（没有确认抬起的触摸抛出 `InputUnconfirmed` 并停止本次运行），正常的任务注册层会把原因报告出来。但有的辅助流程会自己接住它（例如衣柜自动同步接住扫描器的 `UnsupportedInput`，只写详细日志并返回失败，调用方再用已保存的数据继续）。任何能直接或间接走到这类流程的任务，在加进安卓清单之前都要先审查一遍。
12. **开始过程中换控制器的竞争（既有问题）**：客户端开始一批任务时，如果启动过程中又有一个连接请求（界面上手动连接，或经 WebUI 的 HTTP 接口），有两个已有的竞争：自动刷新已停止的控制器时会用旧的配置盖掉刚连上的新控制器；最后一次代数检查之后、下发任务之前换控制器，任务仍经旧的 Tasker 下发，任务记录却写进已换了控制器的实例。前提是在开始的那几秒里有并发的连接请求；在现在的 Windows 和 Mac 上，这只会是同类型的另一个窗口。B1 在绑定控制器的锁里按当时的连接重新准入，所以换成安卓控制器会被拒绝，但没有改这两处竞争（改它们会改变 Windows 的启动流程）。B5 让客户端真正能选安卓控制器时再评估。
17. **没有确认抬起的触摸**：MaaTouch 通过 `InputManager.injectInputEvent` 注入事件（审查者看过它的字节码），不是虚拟触摸设备；重启 ADB 或看画面都证明不了一个没确认的触点已经抬起。2026-11-26 起改为读设备：`dumpsys input` 能读出注入的触点是否还按着、以及最近派发的事件（见交接的「按住触点的设备读数」）：发送前设备必须没有按住的触点，发送后要看到这次触摸自己的抬起才算确认；运行器在连接之前，如果一次读数显示标记记的就是这台设备（序列号和启动号）、没有按住、没有排队的输入、没有 MaaTouch 在运行，就先记录再删除留下的标记；agent 不自己删除，客户端仍是启动时清除；其余情况仍停下、要人决定（运行器带指纹清除）。剩下的前提：只认在 Android 13 的 BlueStacks Air 上见过的格式，别的模拟器或系统版本上读不出就一律停下（安全，但可能要人来）；同一台模拟器换了序列号或重启过时也要人来；其余记录项见交接的「按住触点的设备读数」。目前触摸确认失败从没在正常运行中发生过。
15. **截图依赖连接时的网络状况**：截图方式（RawWithGzip）不依赖模拟器连回电脑，但如果以后改回或加上 RawByNetcat，模拟器的网络在运行中变化会让截图失败、任务停止（安全的结果，不会乱点）；不会在运行中换方式。
16. **客户端提交时的任务选项（放开 Adb 准入时要验）**：`utils.rs` 里写着安卓上提交时把管线覆盖换成 `{}`，但提交处现在仍原样转发任务的覆盖；准入关闭时走不到。客户端接线那一步要测：带非空覆盖提交只读检查，客户端要么拒绝、要么实际提交的就是 `{}`（审查者在 B5b 记录）。
18. **客户端的 `owner.lock` 检查可能误判为占用**：客户端在开始和收尾时短暂拿一下 `owner.lock` 再放开；如果这期间另一个线程正好启动子进程，子进程在 exec 之前会继承这个文件描述，锁看起来仍被占用（实现者实测）。结果是开始被拒绝或收尾多等一会，是安全的；窄窗口里也可能让 agent 第一次拿锁失败（agent 停下、不发输入）。
19. **收尾卡住**：Tasker 10 秒内停不下来时仍会被丢弃，框架的销毁可能让收尾线程卡住，槽停在收尾（安全：之后的开始都被拒绝）；`owner.lock` 被别的进程（例如开发用的运行器，使用不同数据目录时不会）一直拿着时，这个实例的开始、重连、断开、销毁都会一直被拒绝，直到锁放开。
20. **连接中的标记提前消失**：HTTP 调用方在连接进行中断开时，「连接进行中」的标记会提前去掉；开始在提交前还会核对控制器句柄没变，所以最多是用新连接开始。
21. **别的东西同时向同一台模拟器发输入**：客户端和开发用运行器（默认用不同的数据目录，各自的 `owner.lock` 互不排斥）同时运行的情况，第三轮复审之后由设备锁拒绝（见「实现和设备验收」；第四轮之后锁固定在 `/tmp`，与 TMPDIR 和数据目录无关）：后开始的一方的任务开始被锁拒绝，不发任何触摸。更正：后开始的客户端在开始被拒绝之前可能已经连上模拟器、启动了 MaaTouch（连接本身不发触摸）。剩下的前提是 MaaNikki 以外的东西在注入输入（另一个自动化工具、开发者手动 `adb shell input`，或者用不同的地址连接同一台模拟器，比如 `localhost` 和 `127.0.0.1`，这不在范围内）：这时一方的判断截图可能被另一方改掉，依据过时页面的触摸仍可能发生。
22. **运行开始之后另一个请求销毁了实例**：要另一个请求恰好在空闲检查之后、提交之后才删实例（另一个前端或 HTTP 调用方）；这时回调找不到实例，槽停在运行中，已经启动的 agent 仍按自己的守卫继续，直到按实例 ID 停止。不是「拒绝即安全」的结果，但 agent 的每次触摸仍然经过截图判断和守卫。
23. **重复的开始被拒绝后，前端的回滚会停掉正在进行的那一轮**：要另一个前端或过时的调用方对同一个实例再按开始；被拒绝的那次不发任何触摸，但前端随后调用的停止会停掉正在运行的那一轮（停止走协作式的停止，见第 2 项第二轮的修改）。
24. **异常退出时不能证明 agent 子进程已经退出**：握手期间关掉客户端时，`kill_on_exit` 没有可以结束的子进程（收尾中的子进程现在由退出在等待之后结束，见「实现和设备验收」）；强制结束时忽略了 `kill`/`wait` 的错误。`owner.lock` 拿不到时下一次开始会被拒绝（安全）；锁能拿到只说明没有 agent 持有它。
25. **桌面开始流程的正向测试不全**：新增的桌面入口测试覆盖了没有 Tasker 时的停止和没有连接时的各操作，没有覆盖成功开始返回的任务 ID、重连和真实回调对 agent 的影响（需要 tauri 的 AppHandle，测试里没有）；共用函数的改动只有入口分支，Windows 行为靠 CI 和代码审查把关。HTTP 设备验收也没有经过工具栏、定时任务和自动重连。
26. **开始请求还在路上时按停止（第二轮复审 3）**：前端已经提交开始、后端还在读请求或做准入、还没取得运行槽时按停止，后端看到槽空闲，停止什么都不做；开始随后取得槽、提交任务。工具栏在开始的响应回来之后发现期间按过停止，再停一次。第三轮复审之后这次补发的停止一定会发到后端（以前它会并入之前那次还没返回的停止，后端收不到第二次）。剩下的窗口：从取得槽到开始的响应回到前端、补发的停止到达后端，这一轮照常运行。其间发出的触摸是普通的受守卫触摸：每次都依据当时的截图判断、经过页面守卫和触摸确认，停止本身不会切断触摸（走上面的停止路径）。
27. **并发的调用方（第二轮复审 12，即第 22、23 项）**：两条仍然成立，前提都是另一个前端或 HTTP 调用方同时操作同一个实例。只有重复的开始是「拒绝即安全」：被拒绝的开始不发触摸，前端回滚触发的停止走上面的停止路径（标记没消失时结束 agent 而不 `post_stop`），不会因此留下按住的触点，但会停掉正在进行的那一轮（第 23 项）。销毁实例那一种不是安全的拒绝：空闲检查之后另一个调用方提交了，销毁仍会删掉实例，agent 继续按自己的守卫发触摸（见第 22 项）。
28. **点击卡在按下和抬起之间时进程没了（第三轮复审 1）**：ADB 卡住，一次点击在按下之后超过 10 秒还没发出抬起时，如果进程被强制结束（`kill -9`、崩溃），或者客户端退出等满了 10 秒的上限后继续退出，触点可能留在按下的状态。客户端的停止和运行器（第三轮之后）都不会在 Tasker 停下之前主动退出，所以剩下的是这两种：强制结束，和客户端退出时超过上限。收窄（第四轮复审 1、6）：崩溃或 `kill -9` 在按下和抬起之间的任何时刻都可能留下按住的触点，10 秒这个前提只针对客户端有序的退出；运行器在标记已清、`stop.request` 写成功之后，`post_stop().wait()` 超时会直接去收尾，不再等 Tasker 停下（这时预留已经清掉，停止请求挡住新的触摸，对触摸是安全的）。后果有边界：下一次运行在截图之前读设备的触点状态，看到按住的触点就什么都不发、停止所有输入，要人来处理（风险 17）。
29. **补发的停止的回复晚到，停掉下一轮（第四轮复审 1）**：前提是工具栏补发的停止（风险 26）的后端回复，晚于用户下一次按开始才回到前端。结果：前端随后的收尾再发一次停止，刚开始的下一轮被停掉。设备上的样子：日志里一轮刚开始不久就收到停止并结束，前面紧挨着上一轮的两次停止。停止路径本身不发任何输入；如果这次停止在下一轮第一次触摸之前到达，下一轮一次也没点；回复拖得更久时，下一轮在被停掉之前可能已经发出过正常的、经过守卫和当前截图判断的触摸（安全：没有绕过守卫的输入，只是这一轮被提前停掉）。
30. **超时处理入口的信号跳过停止握手（第四轮复审 3，只涉及运行器）**：任务超时进入 `except RunnerError`、还没开始推迟信号的那几微秒里收到 SIGTERM，`KeyboardInterrupt` 从处理里抛出，收尾照常但不调用 `stop_tasker`。前提是信号恰好落在这个窗口，而且点击此时卡在按下和抬起之间、收尾期间一直没恢复；后果同风险 28（下一次运行读到按住的触点就不发输入）。
31. **退出时桌面子进程的清理先跑（第三轮复审 2，部分修复）**：窗口销毁时先清理桌面的子进程，它可能在 `child.wait()` 上阻塞并持有实例锁；这期间一个已经拿着槽锁、等实例锁的安卓提交，在清理放开锁之后、退出关闭准入之前提交任务。前提：退出时恰好有一次安卓开始在握手中，同时桌面子进程的清理阻塞。提交的这一轮随后由退出走正常的停止。
32. **停止请求写失败时，并发的第二次停止先返回（第三轮复审 4，部分修复）**：`stop.request` 写不进去时，第一次停止要结束 agent；在它结束 agent 之前，同时到达的第二次停止看到「收尾中」就返回 Ok，这时 agent 还可能预留一次受守卫的触摸。前提是写文件失败和两次停止并发同时发生；触摸仍经过截图判断和守卫，不会因停止本身被切断。
33. **奇迹之旅的快捷入口不过危险词检查（月卡第一轮复审 1，记录）**：`rt.key("monthly")` 走按名字的 HUD 动作，确认快捷栏标签后直接点，不查 `MaaNikki_Android_Forbidden`；和邮件任务的 `key("menu")` 是同一条路径（阶段 B 审过）。前提是一张被认成大世界、快捷标签读得到、而且标签 40 像素内有「购买」之类字样的画面；真实 HUD 上「共鸣」就挨着「奇迹之旅」，按整框做危险词检查会把正常入口也拒掉，所以没有加。安全靠快捷标签的居中窗口复核（偏向「共鸣」的点会被拒）和点之后核对到达的是「奇迹之旅」页面。
34. **关奖励层那一点没有设备上的逐点证据（月卡第一轮复审 5，记录）**：关闭点 (600,705) 是从第一次设备运行点中的 (640,700) 左移到同一条空白带上的，测试用的拼图在这一点上是合成背景，这一点本身没有在设备上点过。前提是布局和已存帧一致但这一点点了不关；结果是安全的：每次领取最多点一次，层还在就停下、不再点。以后可以加一张覆盖这一点、两个页签和奖励层的小裁剪来独立核对。
35. **没见过的按钮颜色可能被当成「已领取」（月卡第一轮复审 6，记录）**：「一键领取」按钮区域金色不超过 5% 就当作按钮熄灭或不在；如果领取后按钮换成没见过的颜色（审查者用饱和的蓝色模拟），而页签和内容都还认得出，任务会报告领取成功并继续往下走。前提是这种外观真的出现；不会因此多点一次领取，只会多切一次页签和回大世界，都经过守卫。
13. **源码包不含 `resource_android/`**：`scripts/release.py` 的源码目录清单（`SOURCE_DIRS`）没有它，现在发布的源码包里没有安卓资源（`agent/host/android` 和 `scripts/android` 在 `agent/`、`scripts/` 下，已经包含）。真正发布安卓支持之前要补上，与阶段 F 的发布方式一起决定（改它会改变 Windows 发布物里的源码包）。
11. **资源缓存顺序**：附加资源要在第一次识别之前加载完，否则已缓存的匹配不会更新（审查者在 5.16.1 上验证）。
9. **账号能到达的页面有限**：乐园构想点不开（Mac 测试时确认锁定），日历里「每日幻境」显示尚未解锁，菜单里没找到奇迹之冠。这些任务在安卓上的验证要等对应内容可用，或换一个账号。
10. **游戏更新**：手机和 PC 版本同步更新，手机资源要和 PC 资源一起维护，工作量随资源数增长。
