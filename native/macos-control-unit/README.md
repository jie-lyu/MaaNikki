# Mac 控制模块

[macOS 支持计划](../../docs/macos-support-plan.md)

Mac 版使用基于 MaaFramework 源码打补丁、自行编译的 `libMaaMacOSControlUnit.dylib`，其余库沿用官方运行时。只替换这一个文件：工厂函数签名和版本号与官方一致，官方主库按文件名加载它。Windows 构建不涉及本目录。

| 文件 | 作用 |
| --- | --- |
| `upstream.lock.json` | 锁定 MaaFramework 标签与提交、MaaUtils 子模块提交、MaaDeps 预编译依赖和官方运行时的 SHA-256。 |
| `patches/` | 按文件名顺序应用到上游源码的补丁。 |
| `build.py` | 下载并校验源码与依赖，应用补丁，编译控制模块。 |
| `probe.py` | 开发探针：通过官方主库驱动控制模块。`windows`、`lifecycle`、`capture`、`hit-test` 不发送输入；`input-check`、`camera-check`、`scene-button-check` 向游戏发输入，只在维护者在场并同意时运行。 |
| `test_probe.py` | `scene-button-check` 的离线测试：用假控制器检查会发什么、按什么顺序、任何失败下按键与鼠标键都会松开。 |

## 补丁内容

`0001` 增加两个只有本构建认识的取值，官方取值的行为不变。官方控制模块收到这两个值时会报「Unknown method」，之后既不截图也不发送输入，不会悄悄换成别的行为。

| 取值 | 行为 |
| --- | --- |
| 截图 `1 << 1`（DisplayWindow） | 方法 A：按窗口所在显示器过滤出这一个窗口，`sourceRect` 取窗口在该显示器内的可见部分，按真实像素输出。缓存窗口查找和过滤器；每次截图先用 CGWindowList 和 CGDisplay 比对窗口位置、显示器位置和显示模式，有变化才重建；截图期间几何变化时丢弃这一帧。 |
| 输入 `GlobalEvent \| PostToPid`（Hybrid） | 按键和文字发给游戏进程；绝对坐标的鼠标走全局事件，不激活窗口；相对移动发给游戏进程。必须与 DisplayWindow 截图一起使用。 |

只在前台工作：按键、文字、相对移动和点击都要求游戏是最前面的应用（`GetFrontProcess`，已弃用但仍可用；辅助功能的「当前焦点应用」在部分应用前台时会失败，`NSWorkspace` 在没有主循环的进程里不会更新）。

按下之前先把光标移到目标点并等待 0.3 秒，然后重新做下面的全部检查再按下：实机上游戏按悬停位置处理点击，而不是按下事件携带的坐标，直接按下会点中原先悬停的控件（Windows 版同样先悬停 0.3 秒再点击）。点击坐标按最近一帧的原点和缩放换算到桌面坐标，截图和点击共用同一套数据，每个偏移只加一次。按下前还要满足：

- 有可用的帧，并且连接以来窗口和显示器几何没有变过。点击只带坐标，无法知道它是按哪一帧算的，所以几何一旦变化就锁定，直到重新连接、重新识别；
- 窗口仍在，窗口位置、显示器位置和显示模式与该帧一致；
- 坐标在画面内；
- 用辅助功能按坐标命中测试，接收点击的是游戏进程，而不是 Dock、菜单栏或别的窗口。窗口列表无法用来判断：本机就有三个应用在所有窗口之上放着全屏的透明窗口，点击会穿过它们；
- 在游戏进程自己的窗口里，该坐标最前面的是已连接的窗口；
- 命中测试可能阻塞，最后再确认一次游戏仍在最前。

任一不满足就不发送。松开只跟随被接受的按下，位置和进程与按下时相同，并且总是发送；发不出去的松开继续记为按住，下次再试，并把失败报告给调用方（`inactive()` 返回失败；由持有控制器的客户端据此要求重新连接，尚未实现）。控制模块仍记为按住的键再次按下时会重新发送按下，不会因为 agent 绕过它直接松开过而吞掉这次按键。拖动只跟随被接受的按下。主库停止时会在另一个线程直接松开按键，所以全部状态由一把锁保护；按下前的悬停等待和随后的第二次检查都不持锁（命中测试可能阻塞），期间停止线程送来的松开立即发出并取消这次按下，按下前持锁核对；停止线程送来的松开总会取消该键或该鼠标键的下一次按下，无论多晚到达，即使当时还按住着更早的一次（主库可能已经登记了新的按下）；控制模块仍记为按住的键，只会向记录的那个进程重新发送按下，窗口换了进程时拒绝，并保留原进程用于松开；任务结束时主库排在其后的 `inactive()` 清掉没被用掉的取消记录。`inactive()` 和销毁时松开仍按住的键和鼠标键。
最短按住时间：来自任务线程的松开会等到按键或场景鼠标键已按住 40 毫秒再发出（长于 30 帧时的一帧 33 毫秒；实机上 12 毫秒的按键被游戏漏掉，游戏每帧读一次输入）。取值偏低是因为导航引擎的微调转向按键脉冲从 28 毫秒起；主库的 ClickKey 本身按住 50 毫秒，不受影响。最终取值待实机调整。停止线程送来的松开从不等待；但主库的 ClickKey 在进入控制模块的 `key_up` 之前已经取走了自己的自动释放记录，停止若恰好落在补足的时间内，要等任务线程发出松开，这是有限的延迟。点击不受影响：悬停的 0.3 秒在按下之前，按下之后主库照常保持 50 毫秒。

悬停（补丁版本 3）：不带按下的 `touch_move` 是悬停：与点击一样检查该点，把光标移过去并停在那里（agent 悬停卡片读取浮窗、把光标停放到别处都靠它），第一次悬停前记下用户的光标位置；之后的按下或滚动结束时把光标放回这个位置，任务结束的 `inactive()`、`release_all()` 和销毁也会放回。有鼠标键按住（场景键）时不悬停，以免移动光标转动镜头；某个触点的按下被拒绝后，直到它的 `touch_up`，该触点的移动也不悬停（主库的拖动在起点被拒后仍会发后续移动）。按下或滚动一开始就接管保存的位置，并发的清理不会再放回一次；放回失败时保留，下一次清理重试。停止或任务结束（`inactive()`、`release_all()`）同时忘掉悬停登记的滚动位置，只有真正发生了的悬停才登记滚动位置。悬停只用于界面：控制模块分不清库存页和大世界，调用方要先确认当前页面。

滚动（补丁版本 3）：主库执行滚动时先发一次不带按下的 `touch_move` 表示「移到滚动位置」（即一次悬停），再调用 `scroll(dx, dy)`，`scroll` 用掉这个坐标：与按下相同，先检查、移到该点、等待 0.3 秒、再检查，然后经全局 HID 事件流按行发送滚轮（Windows 的 120 个单位记为 1 行，不足一行按 1 行），等 50 毫秒让窗口服务器把滚轮交给光标下的窗口，再把光标移回。没有坐标、坐标已被用过、有键或鼠标键按住（按住的修饰键会把滚轮变成缩放等）或任一检查不通过时不发送。等待和第二次检查同样不持锁，期间别的线程送来的松开（停止）会取消这次滚动；但主库停止时如果没有按住的东西，控制模块收不到任何信号，滚动不能当作一定可被停止。

场景鼠标键（补丁版本 3）：`touch_down` 的 pressure 为 `kScenePressPressure`（0x4D4E5343）时，在光标当前位置按下该按键（0 左、1 右、2 中），不做悬停移动：场景里游戏隐藏光标，任何移动都会转动镜头。要求游戏在最前、光标在已连接窗口内、命中测试和游戏自己的窗口列表都指向该窗口，几何未锁定；这些检查不持锁执行，期间停止线程的松开会取消这次按下。按下后与点击一样记为按住，由同一触点的 `touch_up`、`inactive()` 或销毁松开；场景键按住时不接受拖动（`touch_move`），以免移动光标转动镜头。agent 必须用关键字参数调用 Python 绑定的 `post_touch_down(x, y, contact, pressure)`，位置参数写错会按成别的键。agent 用它按能力键（如鼠标右键），只在 `maanikki_patch` 不低于 3 时使用。

每次被接受的按下在日志里写一行 Info（`hover settled, press accepted`），记录各阶段用时：第一次检查（及其中几何、命中测试、窗口列表各占多少）、移到目标点、等待、第二次检查、按下；悬停中途放弃时写一行 Warn，说明原因和光标是否移回。每次松开写一行 `release posted`，记录用时和光标恢复结果（`restored` 表示移回后读到的位置与原位置相差不超过 1 点）。等待按截止时间计算：按 10 毫秒分段睡眠会累积误差，在自建窗口上实测 30 段用了约 350 毫秒，改为截止时间后为 300–303 毫秒。在自建窗口上，同一条按下路径（第二次检查时光标停在目标上）总计约 0.37 秒，命中测试第一次约 127 毫秒、之后不到 1 毫秒。

Intel 上的持续集成：GitHub 一直没有给这个仓库分配 Apple silicon runner，CI 改在 Intel（`macos-15-intel`）上分两步跑，各自只证明它名字里写的那件事：`build.py --unit-only` 交叉编译 arm64 单元，检查加载命令和架构（`lipo -archs` 必须只有 arm64），不执行；`build.py --tests-only --test-arch x86_64` 在独立的源码目录、构建目录和 MaaDeps（锁文件里的 `maadeps_x64_tests`）中，用同一份源码和补丁构建并运行 x86_64 的输入逻辑测试，它不是发布出去的二进制。CI 上传交叉编译出的单元和它的清单；如果发布的就是 CI 产出的这一份，必须先在 Apple silicon 上用同一 SHA-256 的文件对官方主库跑生命周期探针。本机默认的 `build.py`（不带这两个参数）不变：构建 arm64 单元并在本机运行测试。

补丁同时带了 `HybridInput` 的确定性测试（`test/maanikki/HybridInputTest.mm`，CMake 选项 `MAANIKKI_UNIT_TESTS`）：用假的平台层驱动停止与按下的各种先后顺序和全部拒绝路径，不截图、不发送任何事件。`build.py` 默认构建补丁版时会编译并运行它（`--unit-only` 跳过，`--tests-only` 只跑它），失败即中止；测试程序不进入产物。

已知限制（主库行为，控制模块看不到）：停止如果发生在主库登记这次按下之前（例如还在换算点击坐标），主库没有可松开的东西，控制模块也收不到取消，之后这次点击仍可能发出；主库在任务结束时只在没有待执行任务时才调用 `inactive()`，并且先公布任务结果、再清理，也不检查清理结果，停止时这次投递还可能被拒绝。因此要由持有控制器的 Rust 客户端在停止后自行确认控制模块已松开全部输入（带期限，对端不回应也要能结束），未确认前不复用这个连接（第 4 步处理）。

`get_info()` 增加 `maanikki_patch`（当前为 3），agent 据此区分本构建和官方控制模块，并要求版本不低于 2（场景鼠标键要求不低于 3）；还增加 `geometry_changed`，主库每次取控制器信息时实时读取，几何锁定后为真，agent 据此停止任务并提示重新连接。

## 编译

需要 Xcode 命令行工具和 git。`cmake` 与 `ninja` 由脚本用 pip 装进工作目录下的虚拟环境，不安装到系统。

```sh
python3 -I native/macos-control-unit/build.py --runtime-out .build/macos-control-unit/runtime
```

- 产物在 `.build/macos-control-unit/out/patched/`，`build.json` 记录应用的补丁和产物哈希。
- `--stock` 不应用补丁，编译上游原版，用于先确认工具链本身没有问题。
- `--runtime-out` 下载同一标签的官方运行时，核对哈希后写出一份只替换了控制模块的副本，供 `probe.py` 和开发运行使用。目标目录必须是新的、空的，或者是本脚本以前写出的目录，脚本不会删除其他目录。
- 产物使用与官方相同的 `@loader_path`、`@executable_path` 两条运行路径，依赖只能来自 `@rpath` 或系统库，脚本编译后会检查。
- 重复使用工作目录时，脚本会还原上游源码并检查 MaaUtils 没有本地改动，但信任已解压的 MaaDeps。CI 和发布构建使用全新的 `--work` 目录。

升级 MaaFramework 时，同时更新 `upstream.lock.json` 中的全部条目，重新生成补丁，并用 `--stock` 和 `probe.py` 重新验证。

## 验证

```sh
python probe.py windows --runtime .build/macos-control-unit/runtime
python probe.py lifecycle --runtime .build/macos-control-unit/runtime --profile maanikki --game \
    --log-dir /tmp/probe-log --expect-unit <build.json 中的 sha256>
python probe.py refusal-check --runtime .build/macos-control-unit/runtime --profile maanikki \
    --window <一个不在前台的应用的窗口> --out /tmp/refusal
```

`--profile maanikki` 使用补丁新增的截图和输入取值；不加时是官方取值，在补丁版里走的也是官方代码。

`probe.py` 需要已安装 `maafw` 的 Python，并且宿主应用已获得「屏幕录制」权限。`lifecycle` 报告每轮的连接结果、画面尺寸和截图延迟。只有同时满足以下条件才算通过：至少两轮，每轮都连接成功并截到画面；新日志里控制模块的创建与销毁次数都等于轮数；进程中实际加载的主库和 MaaUtils 与 `upstream.lock.json` 一致，控制模块的哈希等于 `--expect-unit`（`stock` 表示官方版）。截图失败时不读取主库缓存的上一张图。

`hit-test` 不发送任何输入：把 1280×720 画面上的一组点按补丁的截图几何换算到桌面坐标，报告辅助功能命中测试在每个点给出的进程，以及当前最前面的应用。`refusal-check` 在目标窗口所属应用位于前台时直接退出；否则点击、按键和相对移动都必须被控制模块拒绝并记录日志。`refusal-check` 是「预期拒绝」测试：前台检查只在开始时做一次，运行期间如果目标应用被切到前台，输入就是真的，所以目标请用无关紧要的窗口。`input-check` 会向游戏发送按键和点击，只能在维护者在场、同意后运行：等待游戏回到最前（不会主动激活），每一步都用截图确认上一步的结果，第一处失败就停止并以非零状态退出：只有截图里认出大地图的返回按钮（`fixtures/map-back-button.png`）才点击，点击后它必须消失才继续。M 按住约 80 毫秒：实机上 12 毫秒的按键被游戏漏掉了。

`scene-button-check` 在光标当前位置按场景鼠标键（不移动光标），只在维护者在场、同意后运行；开始前要求补丁版本不低于 3、光标在游戏窗口内，并先截两张静止帧估计待机动作带来的画面变化。中键（默认）先用相对位移把镜头转开再按，判读镜头是否回正；左键（净化）和右键（当前选中的能力）不转镜头。右键必须写 `--expect-ability`（如 `insect`）：探针先按 agent 的方法读右下角的能力按钮，不是这个能力就什么都不按；加 `--select-slot N` 时先按该槽位的数字键（游戏默认键位 1–8）再读一次，仍然不是就停止；光标位置在按任何槽位键之前检查，按下前的最后一帧上再确认一次能力。`--hold` 是每次按住的秒数（0.05–3），按住 0.4 秒以上时在按住期间多存一帧，输出里的 `measured_hold_s` 是从按下得到确认到请求松开的间隔（含按住期间的截图），可作为游戏里按住时长的下限；`--repeat` 连按次数（1–8，间隔 0.15 秒，接近钓鱼收线的节奏）；`--with-forward` 在第一次按下前按住 W、最后一次松开后才松开（移动中按键）。每个已提交的按下（鼠标键、W、槽位键）无论之后发生什么（失败、异常、Ctrl+C）都会请求松开；松开没有得到确认（被拒、出错或等待时被中断）就调用 `inactive()` 松开全部并停止。结果都标为待判读：日志里每次按下要有 `scene press accepted` 和成对的 `release posted`；游戏是否每次响应由现场观察判断，保存的画面只截在按下前、长按期间和松开 1 秒后，短动作可能已经播完。

`key-sequence-check --sequence face-camera|starsea-fall` 向游戏发 agent 自己的按键序列（只在维护者在场、同意时运行）：`face-camera` 与 `ForegroundInput.face_camera()` 相同（按住 Ctrl，W 点按 80 毫秒，先松 W 再松 Ctrl），`starsea-fall` 是 `resource/routes/macros/starsea_fall.json` 去掉开头 1 秒等待（空格约 0.16 秒，间隔约 0.23 秒，Q 约 0.10 秒）。两者都假定游戏的默认键位（前进 W、跳跃空格、急坠 Q）。等待按 agent 的方式计时：`face-camera` 从提交 W 之前开始算 80 毫秒（与 `face_camera()` 相同），`starsea-fall` 在每次按下返回之后等满整段（与路线宏的执行相同）；`face-camera` 在松开 Ctrl 0.4 秒后（agent 判读的时刻）多存一帧。所有剩余按键都会依次尝试松开（后按的先松），只要有一个没得到确认，就在全部尝试之后调用 `inactive()` 并报告结果；结果待判读。`camera-check --record-cursor` 在真实指针随相对位移移动时只记录每一步的位移（`cursor_moved_by`）而不停止，用于查光标漂移的触发条件。`timing [--activity none|user-initiated|latency-critical]` 不发任何输入、不需要游戏和运行时，只测本进程里短睡眠的实际时长，并记录当时最前面的应用和 HID 空闲时间。

界面探针（只在维护者在场、同意时运行；都用 `resource/` 里 agent 自己的识别节点在新截的画面上判断页面，agent 自定义的识别不在其中）：`photo-mode-check` 只在大世界里按 P，只有认出相机界面（`MaaNikki_Daily_PhotoReady`：「大喵相机」标题或模式页签）才按 Esc 退出，从不按快门；`text-input-check` 要求维护者先打开博物图鉴的「检索」且输入框为空（`MaaNikki_CompendiumSearchReady`），每轮点输入框、用单元的 `input_text` 输入（`Ab12`、`星光`），OCR 读回输入框，再点输入框自带的清除按钮，不按 Enter、不用剪贴板、不提交；`hover-check --point X Y` 要求维护者先打开祝福闪光仓库并选中一张卡片（`MaaNikki_Blessing_InventoryReady`），只发不带按下的移动（单元的悬停）：停到 agent 的停放点、悬停到卡片、再停回去，最后用 `inactive()` 把光标放回，比较前后光标位置。
